## 3. The three judgements I was asked for

### 3.1 FT-11 — parity failure, accepted difference, or layout defect?

**A layout defect. Low. Not a MUP-33 failure and not an accepted difference.** Reproduced exactly:

```
revalidation timeline: {"clientWidth":538,"scrollWidth":698,"pageScrolls":false,
 "headers":[{"Model",944},{"Tier",1023},{"Owner",1084},{"Last validation",1203},
            {"Due",1295},{"Days",1367},{"Outcome",1463},{"Status",1554}]}
```

Three separate questions, three different answers:

1. **Is MUP-33 broken?** No. MUP-33 asserts *page* overflow at 1440×900, and
   `document.documentElement.scrollWidth − clientWidth` is **0** on every built screen I swept
   (Command Center, Operations Board, Document Centre, Import Centre, Audit Trail, Admin, Model 360,
   Model Risk Report). `.tablewrap { overflow-x: auto }` (`app.css:80`) is the app's deliberate
   mechanism for a table wider than its box, so a table scrolling inside its own panel is the design
   working, not failing. **MUP-33 stays Match.**
2. **Is it an accepted difference?** No. An accepted difference records a place where the BRD and the
   mock-up disagree. Nothing disagrees here — the mock-up's own revalidation table is full width and
   fits. This is the app disagreeing with itself.
3. **Is the data actually unreachable?** Only visually, and only simultaneously.
   `FT-11_panel_scrolled_app.png` shows every §10 column present and populated once the panel is
   scrolled right — Owner `U-201`, Last validation `7/5/2024`, Due `7/5/2026`, Days `87d overdue`,
   Outcome `Approved`, Status `Overdue`. So **MP-17 is substantively closed**: the values exist, in
   one list, on one screen. What fails is that you cannot see a model's status next to its name.

So: a real defect, of the usability kind, severity **Low** — which matches FT-11's own grading. Two
things make it worth fixing before a demo rather than after. First, the irony: the column that is
entirely off-screen is **Outcome**, the one BL.24 added, so the fix for MP-17 is the part a viewer
cannot see. Second, Windows uses overlay scrollbars, so there is **no visible affordance** — the
panel looks like a table that ends at "OU", not like one that continues.

**What should give.** The panel should leave the two-column grid. It currently sits inside
`<div className="cols">` paired with Governance insights (`CommandCenter.tsx`), and `.cols` is
`repeat(auto-fit, minmax(280px, 1fr))`, which at 1440 gives it 538px. A full-row section gets
~1,160px, and the table needs **698px** — it fits with room to spare, no column dropped, no font
change. That is a one-line move. If the two-up layout is wanted, the second-cheapest change is the
Model cell, which stacks the ID over the full model name and is what forces the 160px shortfall and
the four-line rows; constraining its width (name on one line, ellipsised, full text in `title`)
recovers most of it. I would **not** drop a column: §10 names all of them.

**And it is not a one-off.** The same sweep found a second instance nobody has reported: the
**Document Centre register** clips **Folder** and **Uploaded** (`clientWidth 866`, `scrollWidth
1292`) — visible in this run's own `MUP-38b_app.png`, where the Versions table's Batch column reads
`BAT…`. Two instances make it a pattern, so I have raised it separately as **MP-22** and would fix
both with one rule rather than one panel at a time.

### 3.3 Does the historical-report view mislead a viewer?

**Yes, and the single most harmful element is not a number — it is a sentence.** This is **MP-18**.
It is the same substance as CR-41; I am not re-grading it, I am answering the parity-level question.

Open `MRR-20260831-001` as an Executive (`MP-18_stored_report_app.png`, `MP-18_header_app.png`,
`MP-18_documentation_app.png`) and you read:

- `Business date 2026-08-31 · MRR-20260831-001 · generated by system at 8/31/2026, 5:00:00 AM`
- **Documentation — 0% complete**, with a 250-row table in which M-0001 … M-0009 are each missing
  *Terms of Reference, Model Development Document, Validation Report, Model Approval/MRC Paper,
  Monitoring Plan* — i.e. everything
- **Governance score — portfolio 64.5**, bands 53 / 183 / 6
- and, at the foot of the page, **"Figures reconcile with the Command Center for the same business
  date."**

Three things are wrong with that as a screen, in increasing order of seriousness.

1. **The numbers are an artefact of generation order, not of history.** The seeded report is produced
   before the seed's 1,116 evidence documents load, so only its documentation section is "early".
   Every other section is **today's** portfolio: its stage split is 6/14/18/11/148/31/14/14, its
   revalidation split 8/15/170 and its findings 21/94/33 — *identical, number for number*, to the
   2026-09-30 Command Center. A report dated 30 days earlier whose revalidation statuses are those
   of a month later is not a point-in-time snapshot of anything. The portfolio score difference
   (64.5 against 92.9) is therefore not a story about governance improving; it is one input missing.
2. **The screen invites exactly the wrong reading.** The two reports sit one row apart in the same
   table, with no label distinguishing "generated by the system as a baseline" from "generated by a
   person". A viewer's natural inference from 64.5 → 92.9 in 30 days is dramatic improvement, and a
   demo audience will say so out loud.
3. **The footer makes a claim that cannot be true and cannot even be checked.** "Figures reconcile
   with the Command Center for the same business date" is rendered at page level, *outside*
   `ReportView`, so it is asserted over whichever report is open. For `MRR-20260831-001` it is false.
   Worse, it is **unverifiable by construction**: the Command Center has no as-of control and always
   renders `app.clock.today()`, so no Command Center for 2026-08-31 can be produced by this
   application at all. The claim is sound for a freshly generated report and meaningless for every
   other row in the table — and a governance tool asserting reconciliation it cannot demonstrate is
   worse than one saying nothing.

For completeness, the same report **is** right about the things it should be right about: today's
`MRR-20260930-001` matches the Command Center figure for figure (§6), REG-15 holds, and
"Changes since the previous report" correctly reports 4 models added, 3 phase changes and 5 findings
closed against the baseline.

**Suggested fix, smallest first.** (a) Scope the footer sentence to a report generated in this
session, and replace it on a reopened one with something true — "Historical copy, stored as it was
reported on <date>. Not recomputed." (b) Label the seeded baseline in the list as a baseline. (c) The
real fix, for whoever owns CR-41: either generate the seeded report **after** the documents load, so
its only lie disappears, or drop it and let the first user-generated report be the first.
