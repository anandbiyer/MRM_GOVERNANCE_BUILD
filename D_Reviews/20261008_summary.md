## Why the criteria count is 73, not 74

The test reviewer measured **74 proven** and graded **REG-16 Proven**, on green CI. The functional
tester then demonstrated REG-16 **failing** against a real seeded predecessor. Both are right about
what they measured, and the functional evidence governs: the CI test
`test_reg_16_the_same_data_gives_the_same_content_hash` is green because the `loaded_client` fixture
holds no stored report, so both generations hash an empty change section. **The fixture, not the
code, is what makes it pass.**

So for this summary: REG-15 **Proven**, REG-16 **Failing**, REG-17 **Weak** (TR-37). Net movement
from the Gate 0 exit is **+1 Proven**, not +2.

This is worth stating plainly because it is the second time this gate that a green test turned out to
prove nothing, and the first was found by the same chain: the test reviewer's **TR-39** showed FS-25's
determinism check could not fail, the functional tester fixed it, and **the fixed scenario failed on

## The three demo-visible findings, which converge

**CR-41 = MP-18, and all three agents reached it independently.** The seeded previous report is
generated before the seed's evidence documents load, so with no documents `completeness` returns
`score=0` rather than `None` and the 25%-weight documentation component scores zero for every model
instead of being dropped as not-applicable.

On screen, measured: **0% documentation, 250 of 256 models missing documents, portfolio score 64.5**
against today's **92.9** — while *every other section is today's portfolio, number for number*
(stages 6/14/18/11/148/31/14/14, revalidation 8/15/170, findings 21/94/33, identical to the
2026-09-30 Command Center). A viewer reads 64.5 → 92.9 as improvement, and "changes since" explains
only 4 models added, 3 phase changes and 5 findings closed.

The sharpest point is a sentence, not a number: the footer **"Figures reconcile with the Command
Center for the same business date"** is false for that report *and unverifiable by construction*,
because the Command Center has no as-of control. A governance tool asserting reconciliation it cannot
demonstrate is worse than one saying nothing.

Both testers rank this **above FT-09 for a demo** — FT-09 needs someone to generate twice and compare
hashes; this is on screen the moment anyone opens the report history.

**The author's judgement was wrong on the reasoning, not the placement.** The ordering is forced by
FT-04 (a reset may make no write after starting a background job) and all three agents agree it is the
only lawful placement as written. But two of the three reasons recorded in the code were wrong: the
evidence files are dated across quarters, not the last 30 days, so "they did not exist then" is false;
and REG-16 was not the criterion in play — GEN-01 is, and it holds for a different reason. The
functional view favours generating the seeded report at the tail of the document-analysis job chain,
since FT-04's rule is about writes in `_reset_job` after handover, not work inside a job.

## Recurring pattern worth naming

Three times this gate a locator or assertion was found to be positionally or scope-dependent, and each
time the symptom was a test that could not fail:

- **FS-26** compared the Due cell at `.nth(2)` after BL.24 inserted two columns ahead of it.
- **MUP-34** had the identical defect, found by the parity tester, and is now fixed with a shared
  `cellByHeader()` helper.
- **FS-29's** time-of-day assertion was scoped to the whole `main` element, and the History half was
  vacuous on every run because that tab always renders a Versions list with a time.

All three are the author's. The remedy adopted in the harness — find a cell by its header, assert
inside the element under test — is now shared code rather than three local fixes.
