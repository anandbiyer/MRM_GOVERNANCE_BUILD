## 4. The three findings handed to me — verified and taken over

### 4.1 TR-39 — **Confirmed**, fixed, and it immediately found a real defect

The test reviewer's reading is exactly right. I reproduced it rather than reasoning about it: a
temporary probe installed a route handler that rewrote the **second** `POST /api/reports/model-risk`
response's `content_hash` — a simulated product that generates different content from the same data,
which is precisely what REG-16 forbids — and ran the old and the proposed assertion against it.

```
✓ TR-39 old pattern — cannot see a non-deterministic second generation   (6.0s)
✘ TR-39 fixed pattern — the same defect fails the scenario               (1.8s)
    Expected: "7ecf126c7c6ceec1…"   Received: "deadbeefdeadbeef…"
```

The probe file was deleted after the run; no product code was touched.

Taken over as harness defect **H-17**, recorded in `functional-scenarios.md`. FS-25 now:
identifies the second generation by the **displayed report id** changing (an event that cannot
already be true, unlike "the hash is not empty"), asserts the stored row count rises by one, and
only then compares hashes. While I was there I also closed two gaps in the same criterion that the
reviewer did not name: REG-16's "each generation writes one audit event" and its "nothing is stored
and no audit event is written" on the refusal, neither of which FS-25 asserted.

**The first thing the fixed scenario did was fail — on a real product defect, FT-09.** That is the
return on the fix, and it is the one High in this report.

### 4.2 TR-41 — **Confirmed, and worse than stated**; fixed

The Overview half is as described: `Model360Page.tsx:85` renders tier overrides through
`formatDateTime`, FS-08 applies one to M-0012, nothing resets the database between suite runs, and
alphabetical file order is all that keeps `dashboards.spec.ts` ahead of `inventory.spec.ts`.

The audit half is **not** state-dependent — it is vacuous on every run. The History tab always
renders a **Versions** list through `formatDateTime` (`Model360Page.tsx:187`), and every model has
at least one `model_version` row, so `expect(historyTab).toMatch(HAS_TIME)` scoped to `main` was
satisfied by the Versions line irrespective of what the audit table did. It never had teeth.

Taken over as harness defect **H-18**. Each time-of-day assertion is now scoped to the element that
renders the field under test: the Lifecycle panel's first `<li>`, the Audit history table's first
"When" cell, and the Governance score heading. The Score assertion also gains the `HAS_TIME` check
it never had. FS-29 still passes.

### 4.3 CR-46 / TR-40 — **Confirmed**; **nothing on screen is affected**

Reproduced on the live API:

```
generated_at                              -> "2026-10-08T11:11:00Z"      aware
sections.changes_since.previous_generated_at -> "2026-10-08T11:10:51"    naive
```

So BL.28's `Utc` annotation does reach the declared field and does not reach the one inside the
untyped `sections: dict`, exactly as CR-46 says.

**No visible symptom, and I checked three places rather than assuming.** `previous_generated_at`
is absent from the TypeScript type (`api/types.ts:495-502`), so TanStack Query carries it and the
screen never reads it; `grep previous_generated_at` over `AC_frontend/src` and over
`AB_backend/app/reports/` returns nothing, so neither the report screen nor the PDF renders it. The
only timestamp a user sees on this screen is `generated_at`, which is aware and renders correctly
("10/8/2026, 7:21:41 AM"). The defect is real and worth fixing as a latent one — a future screen or
PDF that prints the field would print a wrong-by-the-offset instant — but it costs the demo nothing
today.

One related observation, **not** a defect: the seeded report's `generated_at` is
`datetime.combine(business_date, time(9, 0))` with no zone, so BL.28 labels it 09:00 **UTC** and the
list renders it as "8/31/2026, 5:00:00 AM" in a UTC-4 browser, and would read 2:00 AM in Los
Angeles. That is correct behaviour for an instant; it is only that the chosen instant was meant as a
local 9 a.m. Cosmetic, on seeded data only.

## 5. CR-41 on screen — how bad it is for a demo

This is the judgement the caller asked for, so it gets its own section. I rebuilt the database from
empty, reset, and then walked the screen as a demo audience would: open **Model Risk Report**, see
the one earlier report, open it, scroll.

**The figures are as CR-41 predicts.**

| | seeded report `MRR-20260831-001` | today `MRR-20260930-001` |
|---|---|---|
| Documentation | **0% complete** | 63.6% complete |
| Models missing documents | **250** of 256 | 92 |
| Portfolio governance score | **64.5** | 92.9 |
| Score bands (below 60 / 60–80 / 80+) | **53 / 183 / 6** | 2 / 16 / 224 |
| Weakest component, all ten lowest-scoring | **documentation** | mixed (documentation, validation currency, issue remediation, MRC compliance) |
| Changes since the previous report | — | 4 models added, 3 phase changes, 5 findings closed |

**My judgement: bad, and bad in the specific way that is hardest to recover from in front of a
customer.** Four things make it worse than the numbers suggest.

1. **The report looks completely credible.** `screens/CR-41_seeded_report_full.png` is a clean,
   dense, well-ordered board pack with the regulatory framework in the header, 250 models listed by
   name and phase with their missing documents enumerated. Nothing marks it as shaped demo data. A
   reader has no cue to distrust it.
2. **The story it tells is a governance failure, not a cosmetic one.** "A month ago this bank had
   0% of its required model documentation and a portfolio score of 64.5, with 53 models below 60."
   That is the single worst sentence this product can say about its own demo data, and it says it
   in the artefact built for the board.
3. **The recovery is unexplained, and the screen says it should be.** Today's report shows +63.6
   points of completeness and +28.4 points of portfolio score, and "Changes since the previous
   report" — the section whose entire job is to account for the difference — lists four new models,
   three phase changes and five closed findings. It covers models, phases, findings and approvals
   only, so it cannot mention documents or score. The obvious customer question ("what happened to
   the documentation?") has no answer on screen.
4. **The footer makes an explicit claim that is false for this report.** Every report, including the
   seeded one, ends with "Figures reconcile with the Command Center for the same business date."
   The seeded report's figures reconcile with no Command Center that ever existed: they were taken
   from a portfolio that had been emptied of documents seconds earlier and refilled seconds later.
   That is the one place where the defect stops being a demo-data wart and becomes the product
   asserting something untrue.

I have **not** raised this as an FT issue: CR-41 already describes it, it is from this same run, and
my rules say to reference rather than duplicate. What I add is the runtime confirmation and the
severity judgement — **for a customer demo this is the most damaging item in this run, ahead of
FT-09**, because FT-09 is invisible unless someone clicks Generate twice and compares hashes,
whereas this is on screen the moment anyone opens the report history. I would fix it before the
branch merges.

On CR-41's two candidate fixes, the functional view favours the second: seeding the report as the
**tail of the document-analysis job chain** gives a seeded report whose figures are real, and FT-04's
rule is about writes in `_reset_job` after handover, not about work inside a job. Shaping
`documentation` and `score` the way the baseline is shaped would also work, but it leaves a stored
report containing numbers no code can reproduce — which is the harder thing to explain to the next
reader. Whichever is chosen, the footer sentence needs to be true of the report being displayed.

Evidence: `screens/CR-41_seeded_report_full.png`, `CR-41_actual.png` (0% documentation panel),
`CR-41_actual_score.png` (score bands and "weakest component: documentation" ten times),
`CR-41_today_report_full.png`, `CR-41_expected.png` (63.6%), `CR-41_changes_since.png`,
`CR-41_report_list.png`.

## 8. Unspecified behaviour

1. **What "the same data" means in REG-16.** The criterion does not say whether the predecessor
   report is part of "the data". The code has it both ways — the predecessor's *id* is excluded from
   the hash as provenance, the change lists derived from it are included as content. This is the
   substance of FT-09 and it needs a decision, not a guess; I have written both readings into the
   issue. `decision_log.md` and §81A are silent (D12 settles whether the report is built, not what
   its hash covers).
2. **What a seeded report is allowed to contain.** Neither CLAUDE.md nor `decision_log.md` says
   whether a seeded artefact may hold figures that never corresponded to a real portfolio state, nor
   whether it must be distinguishable from a generated one on screen. REQ-REG-10A's "every figure
   equals the Command Center on the same business date" is written for generation, and a report for
   a past business date cannot be checked against a Command Center that only shows today. That gap
   is what lets CR-41 exist. Worth one sentence in REQ-REG-10A.
3. **Whether a stored report may claim reconciliation it cannot support.** The report footer states
   "Figures reconcile with the Command Center for the same business date" unconditionally, including
   on reopened historical reports. No requirement covers the wording of that line.
