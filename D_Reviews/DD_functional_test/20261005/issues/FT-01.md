# FT-01 — Writes fail with "database is locked" in dev mode: SQLite is in rollback-journal mode
Severity: Medium | Scenario: FS-15, FS-21 (collateral FS-16, FS-17, FS-23) | Criterion / BRD §: blocks DOC-01, DOC-02, DOC-17, GEN-02 | Role: Admin | Status: **Verified** 2026-10-07

> **Correction, 2026-10-05 (later the same day).** The first version of this issue blamed OneDrive
> and Playwright's worker count, and recommended `workers: 1`. **Both were wrong.**
> `playwright.config.ts:33` already sets `workers: 1` and `fullyParallel: false` at the top level, so
> the run was serial all along. `MRM_JOB_MODE=inline` does not help either — I tested it and the locks
> persisted. The actual cause is below, and it is confirmed by a decisive experiment: enabling WAL on
> the same database file, in the same folder, with the same thread-mode jobs, takes the lock errors
> from 6 to **0**. The original text is kept in git history rather than rewritten away.
>
> This also moves the issue from "my environment" to a real dev-mode weakness: the same configuration
> is what `start_mrm.ps1` runs, so a user clicking Upload in dev mode can get an HTTP 500.

## Root cause
Layer: backend (dev-mode database configuration) · Location: `app/db.py:9` `configure_sqlite` · Confidence: Confirmed

`configure_sqlite` sets `isolation_level = None` and issues a plain `BEGIN`, which in SQLite is a
**deferred** transaction, and it leaves the database in the default **rollback-journal** mode. In that
mode a reader blocks a writer and vice versa, and — the part that matters here — a connection that
began by reading and then needs to write must *promote* its lock. SQLite refuses a promotion that
would have to roll back another reader by returning `SQLITE_BUSY` **immediately**: the busy handler
is not consulted, so no timeout value would have helped.

The concurrency is not the test runner's. One page load of the SPA fires several API calls in
parallel (`/api/dashboard/summary`, `/api/models/meta`, `/api/models`, `/api/auth/dev-users`), each on
its own connection. When a document upload writes while those reads are open, the promotion fails.
That is why serialising the tests and running jobs inline both changed nothing.

The secondary error, `cannot start a transaction within a transaction`, is a *consequence*: the
connection whose commit raised is returned to the pool still inside a transaction, so the next
`BEGIN` on it fails too. Worth fixing alongside, because it turns one failure into several.

The application's business logic is not at fault: `store_version` commits once, in one transaction,
as the layering rule requires.

## Suggested fix
Two lines in `configure_sqlite`, in the `connect` listener:

```python
dbapi_conn.execute("PRAGMA journal_mode=WAL")    # readers no longer block the writer
dbapi_conn.execute("PRAGMA busy_timeout=5000")   # and a genuine wait is waited out
```

Verified: enabling WAL on the same file, same folder, same thread-mode jobs took the lock errors from
6 to 0, and the document scenarios then failed only on ordinary business behaviour. WAL is persistent
per database file, so this also needs no migration — but set it in code so a fresh `dev.db` gets it.

`busy_timeout` does not fix the promotion case on its own (the busy handler is skipped there), so WAL
is the load-bearing half; keep both, because `busy_timeout` covers ordinary write-write contention.

Running the functional suite against PostgreSQL is still worth doing for fidelity — it is the system
of record (§49) and would have caught the FK-width drift that `0006_document_fk_widths` fixed — but it
is **not** a configuration switch: `functional/helpers/index.ts` reads the database directly through
`node:sqlite`, and all five spec files depend on `dbCount`/`dbQuery`. Pointing the backend at
PostgreSQL while `FT_DB_PATH` still names a SQLite file would leave those helpers reading a stale
database and returning plausible but wrong numbers — worse than failing. That work is its own item.

## Regression test
A backend test asserting that a SQLite engine built by `configure_sqlite` reports
`PRAGMA journal_mode` = `wal` and a non-zero `busy_timeout`. That is a cheap, direct assertion and it
would have caught the omission at the time. Cite BRD §64 (Reliability: "Database writes shall be
transactional") — or, better, add a criterion for it, since §64 has no acceptance criteria today, the
same gap §76A.14 already records for §65.

A concurrency test that reliably reproduces the promotion failure is not worth writing: it needs an
open read transaction in one thread while another writes, which is slow and timing-dependent. The
pragma assertion plus FS-15/FS-16/FS-17/FS-21 passing in one full run is the right level of proof.

## Verification, 2026-10-07 (functional-tester, Gate 0 exit, commit `f89ef6a`)

**Verified.** FS-15 (`DOC-01 DOC-08 DOC-17 single upload, a new version, and a refused duplicate`)
passed in 1.6 s against a freshly seeded test database, and the whole run produced **0** HTTP 500s
and **0** lock errors on the document upload path. `journal_mode=WAL` and `busy_timeout` are in
`configure_sqlite` and take effect on the run's database (`functional.db-wal` present).

The scope limit recorded with G0.17 still holds and is **wider than the plan row states**: the row
says the residual write-against-write case needs "FS-21's second reset while the first is still
loading evidence". It does not. A **single** `POST /api/admin/reset` fails the same way, because
`_reset_job` writes immediately after submitting `analyse_job`. That is a separate issue — **FT-04**
— not a regression of this one.
