# FT-02 — A second reset started while one is running is not refused
Severity: Medium | Scenario: FS-21 | Criterion / BRD §: **GEN-04** (added 2026-10-07, S7), §42 (batch status), §64 (Reliability) | Role: Admin | Status: **Verified** 2026-10-07

> **Fixed.** `start_reset` now refuses with 409 while a reset is in flight, and
> `GET /api/admin/reset/status` reports whether one is running and which batch to watch. Verified
> live: at the instant the caller's own batch reported `Completed`, a second reset returned **409**
> (it previously returned 500), and `reset/status` still reported `in_progress` with the documents
> batch. 6 new tests; suite 178 pass / 4 skip.
>
> Two things found while fixing it, both now handled. The guard alone still had a window: between the
> seed batch going terminal and the documents batch being created, nothing was in flight, so a second
> reset could start inside it — `_reset_job` now holds the seed batch non-terminal across that call.
> And the seed batch *does* return to `Completed` while the evidence is still being stored, so it is
> not a "reset finished" signal; `reset/status` is the one to poll. An earlier version of the code
> comment claimed otherwise and has been corrected.
>
> Not addressed, and worth its own decision: a reset deletes `app_user`, so for a second or two
> nobody can authenticate — existing tokens 401 and even login fails. Any client polling through a
> reset must re-authenticate, and the Admin page does not. Separate from this issue.

Found while verifying G0.17. Separate from FT-01: fixing the SQLite journal mode removed every lock
in the document scenarios, but not this one, because this is write-against-write, not read-against-write.

## Steps to reproduce
1. Sign in as Admin, `POST /api/admin/reset` → `202 Accepted` with a batch id.
2. Poll that batch until its status is `Completed`.
3. `POST /api/admin/reset` again.

## Expected (CLAUDE.md)
> "Failed background jobs shall be retryable. Processing shall be idempotent. Partial batch failures
> shall not corrupt successful records." (§64)

A second reset should either queue, or be refused with a business error naming the reset in progress.
An unhandled HTTP 500 is neither.

## Actual
`POST /api/admin/reset` → **500**, from a 5-second busy-timeout expiry while inserting the batch's
own audit event:

```
sqlalchemy.exc.OperationalError: (sqlite3.OperationalError) database is locked
[SQL: INSERT INTO audit_event (...) VALUES (...) RETURNING event_id, occurred_at]
  app/api/admin.py:35 reset_to_seed
  -> app/services/reset_service.py:102 start_reset
     -> app/ingestion/service.py:115 create_batch
```

The first reset was still writing. The seed batch it is polled on **had** completed — but a reset
produces *two* batches, and the second was still running:

| Batch | Type | Source | Status |
|---|---|---|---|
| B-20260930-005 | seed | reset | Completed ← what the caller is given and polls |
| B-20260930-006 | documents | seed | Completed ← created afterwards by the reset job, 1116 files |

So "the batch I was given has completed" does not mean "the reset has finished". The API gives the
caller no way to know the reset is still in progress, and no guard against starting another.

## Evidence
Log excerpt above, from the G0.17 verification run (commit `2df5c00` plus the WAL change).
Batch table as shown. Both resets did eventually complete, so no data was corrupted in this instance.

## Root cause
Layer: backend · Location: `app/services/reset_service.py:92` `start_reset` · Confidence: Confirmed

`start_reset` has no in-flight check: it regenerates the seed, creates a batch and submits
`_reset_job` unconditionally. `_reset_job` then deletes every governance table and reloads, and
afterwards creates a second batch for the evidence files. Two overlapping runs would interleave
destructive deletes with the other's inserts. On SQLite the second caller fails at the first write;
on PostgreSQL it would block and then proceed, which is worse — it would actually interleave.

## Suggested fix
Refuse the start: in `start_reset`, look for an `import_batch` with `source = "reset"` whose status is
not terminal, and raise a conflict naming it (`ConflictError`, 409), as the optimistic-concurrency
refusals elsewhere do. Returning the in-flight batch id would also let a caller poll it.

Give the caller something to poll that covers the whole reset — either keep the seed batch non-terminal
until the documents batch finishes, or return both ids. The current contract invites exactly the
mistake FS-21 made.

## Regression test
Cite GEN-02. Two tests: `start_reset` while a reset batch is non-terminal is refused with a conflict
and does not submit a second job; and a completed reset leaves no non-terminal `source = "reset"`
batch, so a later reset is accepted. Both run inline (`MRM_JOB_MODE=inline`) like the rest of the suite.

## Verification attempt, 2026-10-07 (functional-tester, Gate 0 exit, commit `f89ef6a`)

**Not moved to Verified, and deliberately not reopened as a Regression.** FS-21 still fails, but not
on this behaviour, so flipping the status either way would be wrong.

What was observed directly:
- The in-flight guard **works**. A second `POST /api/admin/reset` while one was in flight returned
  **409**, naming the batch: `"A reset is already running: batch B-20260930-009 is Validating."`
  (run log, FS-21 retry #1). That is exactly what this issue asked for.
- `GET /api/admin/reset/status` exists and answers.

Why FS-21 cannot pass yet, none of it this issue's doing:
- **FT-04** — an API reset loses all 1,116 evidence documents, so the two resets could not produce
  matching counts even if they both ran.
- **FT-05** — the failed job leaves its batch in `Validating`, so `reset/status` never reports
  `in_progress: false` and the guard refuses every later reset for ever. This is the flip side of
  the guard added here, and the 409 message's advice ("cancel that batch first") cannot be followed.
- **Harness defect H-12** — FS-21's Playwright test timeout is 30 s while its own poll allows 300 s,
  so the scenario aborts before any reset could finish.

Re-verify once FT-04, FT-05 and H-12 are closed.

## Verification, 2026-10-07 (functional-tester, Gate 0 exit **re-run**, commit `779e3de`)

**Verified.** The three things that blocked verification last run — FT-04, FT-05 and harness defect
H-12 — are all closed, and the guard is now **asserted by the suite** rather than observed in
passing.

FS-21 previously carried the tag `GEN-04` without testing it: two *sequential* resets prove
determinism, not a concurrency guard, so the tag was a false coverage signal. The scenario now
probes it directly — while the first reset is in flight (read from `import_batch`, not over HTTP,
because a reset empties `app_user` for a second and nothing can authenticate then), it issues a
second `POST /api/admin/reset` and requires:

- **409**, not 202 and not 500;
- a message naming the batch in flight (`/batch B-\d{8}-\d{3}/`);
- **no new batch row** — the refusal submitted no second job and deleted nothing.

All three hold. 401/403 responses during the window when `app_user` is empty are retried rather than
counted, since they are an unanswered question, not a wrong answer. The criterion the issue should
have cited all along now exists: **GEN-04**, added to §76A.12 on 2026-10-07 as spec issue S7.

The separate observation recorded in the original fix note — that a reset deletes `app_user`, so for
a second or two nobody can authenticate and a polling client must re-authenticate (plan **G0.19** /
**BL.1**) — is unchanged and still open. It is why the probe above has to retry.
