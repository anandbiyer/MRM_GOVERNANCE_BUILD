## 5. Root causes in brief

### FT-04 — the reset loses the evidence (Critical)
`_reset_job` submits `analyse_job` to the thread pool and then immediately commits a status change
of its own (`reset_service.py:194-195`, the hold added by G0.18). The pool has two workers, so both
run at once. `analyse_job` reads the batch items and then flushes — a SQLite **lock promotion**,
which, as G0.17's own comment records, returns `SQLITE_BUSY` *immediately* without consulting the
busy handler. WAL removed the reader-blocks-writer case; G0.18 then placed a real writer next to the
submit, which re-opens the other one.

Measured effect on a clean database, one reset: `document` 0 of 1,116; every model's documentation
completeness 0%; M-0042's governance score **65.9 → 36.5**. CI never sees it, because every backend
test and `app/cli.py:40` force `MRM_JOB_MODE=inline`, which serialises the two jobs.

### FT-05 — the failure is invisible and unrecoverable (High)
`runner._run` logs the exception and moves on; its comment says "job functions record their own
failure", and `analyse_job` does not. The batch stays `Validating` with `error_message: null`, so
`/api/admin/reset/status` reports `in_progress: true` for ever and `reset_in_progress` refuses every
later reset with 409. The refusal advises cancelling the batch — but `EDITABLE` is
`("Ready", "Validation Failed", "Failed")`, so cancel returns 409 too. There is no way out through
the product. `_reset_job` already guards the *seed* batch against precisely this; the documents batch
has no equivalent.

### FT-06 — dates one day early (Medium)
`new Date("2026-09-30")` is parsed as UTC midnight and `toLocaleDateString()` renders it locally, so
every date-only field shifts back a day west of UTC. The Command Center says "as of 9/29/2026" when
the business date is 2026-09-30, and Model 360 shows M-0042's next due as 8/8/2026 while the
Command Center's own timeline shows the correct 2026-08-09 for the same model. Two screens disagree
about the same governance date. Invisible in UTC, which is why CI and the parity run do not see it.

## 8. Unspecified behaviour — for a decision

1. **FND-01's scope.** The criterion says a Closed finding with no closed date "is refused". Create
   refuses; update silently records the business date (`finding_service.py:112-116`, deliberately and
   with a comment). Raised as FT-07 because the criterion and the code disagree, but the fix is a
   decision, not an obvious correction. Related: APR-01 refuses rather than defaulting, so the two
   governance objects behave differently in the same situation.
2. **What a failed background job owes the user.** §42 lists a `Failed` status and §64 requires
   failed jobs to be retryable, but nothing says *who* sets the status when the job itself dies
   before it can. FT-05 is written against §42/§64; a one-line rule in Part 0 ("a job that raises
   marks its batch Failed with the exception text") would make it unambiguous and testable.
3. **The `/api/health` pill blocks for 2 s on every page.** `/api/health` takes **2.01 s** because
   Redis is absent and times out, so the header reads "checking…" for two seconds on every load
   before settling on "system degraded". Part 0 documents the degraded *status* but says nothing
   about the latency. `/api/health/live` answers in 1.8 ms. Worth deciding whether the pill should
   use the live probe first, or whether the Redis check should be given a short timeout. Visible in
   every screenshot in this run's `screens/` folder.
4. **Carried from the first run, still open and still unaddressed by any criterion:** the
   `/api/audit` 1,000-row cap with no `total` (**BL.4**), the Import Centre's `useState` initialiser
   (**BL.3**), and the undocumented `Model_Governance/<Business_Line>/<Model>/<Area>/` evidence path
   convention, which §33 Method A contradicts with its `/M-0012/Validation/` example.
