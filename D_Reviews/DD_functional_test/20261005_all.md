**FT-01 fixed, 2026-10-05 (G0.17).** `configure_sqlite` now sets `journal_mode=WAL` and a configurable
`busy_timeout`. On a fresh database, with the pragmas coming from the code rather than by hand, the
document scenarios produce **0 HTTP 500s and 0 lock errors** (previously 9 and 6), and **FS-15 now
passes** — so DOC-01, DOC-08 and DOC-17 move from blocked to proven. Backend suite 172 pass / 4 skip;
PostgreSQL job 4/4.

FT-01 did **not** fix FS-21, and that is the honest limit of the change: WAL stops readers blocking the
writer, but SQLite still allows only one writer at a time. FS-21 starts a second reset while the first
is still loading evidence files, which is write-against-write. The cause splits in two — a harness
defect (H-10, polling the wrong batch) and a product gap (FT-02, no in-flight guard).

> **Correction, 2026-10-05 (later the same day), while checking G0.16.** FT-01's first diagnosis was
> wrong and its layer has changed from "environment / harness" to **backend**. I had blamed OneDrive
> and Playwright's worker count; in fact `playwright.config.ts:33` already sets `workers: 1` and
> `fullyParallel: false` at the top level, so the run was serial throughout, and `MRM_JOB_MODE=inline`
> made no difference either. The cause is that `configure_sqlite` leaves SQLite in rollback-journal
> mode, where a connection that read and then needs to write cannot promote its lock and gets
> `SQLITE_BUSY` immediately. The concurrency comes from the SPA firing several API calls per page
> load, not from the test runner. Enabling WAL on the same file took the lock errors from 6 to 0.
>
> I also mis-read one intermediate result during that check: an early "0 lock errors with inline jobs"
> was measured against an empty database, so no document work ran and it proved nothing. The 6→0
> comparison above is on a fully seeded database with uploads actually executing.
>
> This matters beyond the test suite: `start_mrm.ps1` uses the same configuration, so a user clicking
> Upload in dev mode can get an HTTP 500. Logged as plan item **G0.17**.

## 5. Unspecified behaviour — for a decision

1. **Import Centre tab default and permissions.** `ImportCentre.tsx:205` sets the tab from a
   `useState` **initialiser**: `useState<Tab>(canImport ? "Upload" : "Templates")`. The initialiser
   runs once per mount, while `can("import:run")` depends on an asynchronously loaded session. The
   tab *list* recomputes on every render but the *selected tab* does not. Today no scenario reaches
   this (H-07 masked it), and I could not make it misbehave with a settled session. CLAUDE.md does
   not say what a screen should show while permissions are still unknown. Worth a decision:
   render nothing until the session resolves, or re-derive the default when it arrives.
2. **Audit endpoint result cap.** `/api/audit` caps `limit` at 1000 with no total count and no
   pagination cursor, so a client cannot tell a complete result from a truncated one. AUD-03 is
   silent on this. H-05 exists because of it. A `total` in the response would make the filter
   assertable and the screen honest about what it is showing.
3. **Document evidence path convention.** Seed evidence is laid out
   `Model_Governance/<Business_Line>/<Model>/<Area>/`, so a document's path depends on the model's
   business line. Nothing in CLAUDE.md states that folder convention, and §33 Method A describes
   `/M-0012/Validation/` without the business-line level. Either the BRD example or the seed layout
   should change so one convention is documented.
4. **Which engine the functional suite runs against.** CLAUDE.md requires the run to avoid the demo
   database but does not say which engine to use. FT-01 argues for PostgreSQL. A decision here is
   also a decision about what CI runs.
