## 5. What I measured, and how

### FT-04 — the reset keeps its evidence (Critical → Verified)

The fix (G0.22) reorders `_reset_job` so the reset finishes every write of its own *before* handing
work to a background job: `stage_seed_documents` creates and commits the evidence batch, the seed
batch's status is restored, and only then does `start_analysis_job` run
(`app/services/reset_service.py:181-213`). The write that used to race the analysis is gone.

I verified it independently of the caller's own check, on three paths and in the mode that failed:

| Path | Job mode | `document` rows | Evidence batch |
|---|---|---|---|
| `python -m app.cli reset`, fresh database | inline | **1,116** | `Completed` |
| `POST /api/admin/reset` inside FS-21, twice per run, across three runs | **thread** | **1,116** every time | `Completed` every time |
| `POST /api/admin/reset` by hand, between runs, to restore the seed | **thread** | **1,116** every time | `Completed` every time |

Eleven resets in total, recorded in `20261007/env_state.txt`. Every `source in ('reset','seed')`
batch ended `Completed` with `successful_records = 1116` and `error_message = NULL`. The backend log
for the whole run — eleven resets, a 400-file document batch, three ZIP and multi-file batches, the
full suite — contains **0** occurrences of "database is locked", **0** tracebacks and **0** HTTP
500s.

The user-visible consequences are back too. Document completeness reads **63.6%, 92 models with
gaps** on the Command Center (`screens/FS-21_after_two_resets.png`); when the defect was live it read
0% with no documents at all. M-0001's Model 360 lists its five seeded evidence files with their
folder paths (`screens/FS-17_completeness.png`).

FS-21 now also carries the assertion whose absence let this ship: `documents > 1000`. The two
snapshots were *equal* when both were zero, so determinism alone passed on an empty Document Centre
— the scenario watched the reset destroy 1,116 documents twice and reported success.

### FT-05 — a failed job is visible, and a wedged batch can be cleared (High → Verified)

Two halves, checked separately.

The **recording** half is wired: `import_service.record_job_failure`
(`app/ingestion/service.py:36-65`) marks the batch `Failed` with the exception text, in its own
session, and never raises; it is called from document analysis (`app/documents/batch.py:235`),
document storage (`:357`) and the reset job's staging (`app/services/reset_service.py:201`) — the
three jobs that previously had none. I cannot induce a crash without editing product code, which I
do not do, so for runtime behaviour this is **Likely**, resting on the three backend tests that
drive it (`tests/test_documents.py:399, :433, :456`). The code path itself is Confirmed.

The **recovery** half I checked live, because that is the half a user needs when it goes wrong. A
400-file document batch was uploaded and, while it was still `Validating`:

```
upload 201 · batch B-20260930-039 status Validating
cancel while Validating: HTTP 200
  -> {"batch_id":"B-20260930-039", … ,"status":"Cancelled", …}
  batch now: Cancelled
```

Under the old `EDITABLE`-only rule that call returned 409, which is what left the application with
no way out of the state FT-04 created. `CANCELLABLE = EDITABLE + ("Validating", "Processing")`
(`app/documents/batch.py:42`) is **Confirmed** working.

And the symptom never recurred: no reset batch was left non-terminal in eleven resets, and
`/api/admin/reset/status` returned to idle every time.

Seven batches *are* non-terminal at the end of the run — all `Ready` document batches from FS-16's
ZIP and folder steps, which stage files and deliberately leave them for review. `Ready` is an
editable, cancellable, correct state, and `reset_in_progress` only looks at `source in
('reset','seed')`, so they block nothing. I checked this rather than assumed it.

### FT-02 — a concurrent reset is refused (Medium → Verified)

Now asserted by the suite instead of observed in passing. While the first reset is in flight — read
from `import_batch` rather than over HTTP, because a reset empties `app_user` and for a second
nothing can authenticate — FS-21 issues a second `POST /api/admin/reset` and requires all three of:

- **409**, not 202 and not the 500 this originally produced;
- a message naming the batch in flight, matched against `/batch B-\d{8}-\d{3}/`;
- **no new batch row**, so the refusal submitted no second job and deleted nothing.

All three hold. 401 and 403 inside the `app_user` window are retried, not counted: they are an
unanswered question, not a wrong answer. The criterion this should always have cited now exists —
**GEN-04**, added 2026-10-07 as spec issue S7.

### FT-06 — dates render their own calendar day (Medium → Verified)

**FS-26**, pinned to `timezoneId: "America/Los_Angeles"`, is well-formed and I have taken it over. It
belongs in `dashboards.spec.ts`: two of its three checks are Command Center screens, and the third
is the cross-screen agreement that was the serious half of MP-10. On the shifted timezone the lede
reads "as of 9/30/2026" for business date 2026-09-30, and the revalidation timeline and Model 360
agree character for character on the same model's due date.

Its `parts()` helper compares the *set* of numbers in a rendered date against the set in the ISO
string, so it is locale-independent but blind to order — "30/09/2026" and "09/30/2026" both match.
That is deliberate and documented; it is worth knowing that it would also not catch a day/month
transposition. I left it as it is: the scenario's job is the offset and the cross-screen agreement,
and both are caught.

I also checked the fix is complete rather than local to the two call sites the issue named. Every
remaining `new Date(...)` in `AC_frontend/src` is on a timestamp (`occurred_at`, `created_at`,
`uploaded_at`), which is correct for an instant. The only place a date-only value still reaches the
user as raw ISO is the Operations Board **CSV export** — which `format.ts`'s own docstring says is
right, because ISO is what a machine should read.

## 6. Unspecified behaviour — for a decision

1. **A reset reuses model ids while keeping the audit trail, so one `entity_id` can hold two
   different models' history.** `M-0257` in this run has two `create` events, 24 minutes apart, for
   two unrelated models: the reset deleted the first, kept its audit events, and the next
   registration was issued the same id. CLAUDE.md is explicit that reset "keeps the audit trail"
   (Part 0) and silent on id reuse. It collides with §67's promise that the trail answers "what
   happened to this record?" and with §46 lineage. Nothing in §76A says which should win, so I am
   not calling it a defect. Options worth a decision: keep the id counter past the highest id the
   *audit trail* has ever seen; or record the reset's generation on the event; or state that reset
   is dev-only and the ambiguity is accepted. It cost a false FS-07 failure once, so whoever reads
   the audit trail after a reset will hit it too.
2. **The `/api/health` pill still blocks for about two seconds on every page**, because Redis is
   absent and the component check times out; the header reads "checking…" in almost every screenshot
   in this run. `/api/health/live` answers in under 2 ms. Part 0 documents the degraded *status* and
   says nothing about the latency. Carried unchanged from the previous run; still worth deciding
   whether the pill should use the live probe first.
3. **What a failed background job owes the user** (carried). G0.23 settled it in code and GEN-05 now
   states it as a criterion — "a background job that fails marks its own batch Failed with the
   reason … a batch left non-terminal by a failed job can be cancelled through the API". This item
   can be closed: the gap that prompted it is filled.
4. **Carried and still open, none of them covered by a criterion:** the `/api/audit` 1,000-row cap
   with no `total` (**BL.4**), the Import Centre's `useState` initialiser (**BL.3**), and the
   undocumented `Model_Governance/<Business_Line>/<Model>/<Area>/` evidence path convention, which
   §33 Method A contradicts with its `/M-0012/Validation/` example.
