# FT-07 — FND-01 is enforced when a finding is created but not when it is updated: the closed date is silently set to today
Severity: Low | Scenario: FS-11 (criterion probed by hand; the scenario itself fails on harness defect H-02) | Criterion / BRD §: FND-01, §11 | Role: Validator | Status: New

Either the criterion should say which paths it covers, or the update path should refuse like the
create path. As it stands the two disagree, and the user is given a date they did not choose.

## Steps to reproduce
1. Sign in as a Validator assigned to a model (U-014 / M-0003).
2. `POST /api/findings` with `status: "Closed"` and no `closed_date`.
3. Create an Open finding, then `PATCH /api/findings/{id}` with `status: "Closed"` and no
   `closed_date`.

## Expected (CLAUDE.md)
> "FND-01 — A finding with status Closed and no closed date is refused."

The criterion names no operation, so it reads as covering both. §11 lists `Closed date` as a finding
attribute and the ageing calculation depends on it.

## Actual
Create is refused, update is not:

```
POST /api/findings  {status: "Closed", closed_date: absent}
  422 {"detail":"Finding for M-0003 could not be saved. Closed date is required when the status is
       Closed.","errors":[{"field":"closed_date", ...}]}

PATCH /api/findings/F-0207  {status: "Closed", closed_date: absent}
  200 — and the stored record reads
       {"status":"Closed","closed_date":"2026-09-30","days_open":60,"days_overdue":0}
```

`2026-09-30` is the business date, supplied by the server. The data invariant "Closed implies a
closed date" is never broken, so this is not a data-integrity problem — but a finding that was
actually closed three weeks ago is recorded as closed today, which moves `days_open` and the
remediation ageing, and no message tells the user a date was chosen for them.

## Evidence
No screenshot: reached through the API, because FS-11 cannot drive the UI form (harness defect H-02,
the button is behind a Model 360 tab the scenario never opens). Probe output is quoted above
verbatim; reproduced on the pristine `env3` database.

## Root cause
Layer: Service · Location:
`A_Codes/AB_backend/app/services/finding_service.py:112-116` · Confidence: **Confirmed**

```python
# Closing without a date defaults to today; re-opening clears the closed date.
if merged["status"] not in open_statuses and merged["closed_date"] is None:
    merged["closed_date"] = today()
```

The default runs before `_validate`, so `governance_rules`' check at
`A_Codes/AB_backend/app/rules/governance_rules.py:20` ("Closed date is required when the status is
…") can never fire on the update path. `create_finding` has no such default, which is why the two
paths differ. It is deliberate and commented — this issue is about the mismatch with the criterion,
not about an accident.

## Suggested fix
A decision rather than an obvious code change. Either:
- **Amend FND-01** to "…is refused on creation and on import; closing through an update without a
  date records the business date", and say so in the UI next to the status control; or
- **Remove the default** so both paths refuse, and have the Model 360 close form pre-fill today's
  date in the field, where the user can see and change it.

The second is more consistent with Part 0's "no business behaviour that the user cannot see", and
with APR-01, which refuses rather than defaulting. I would not choose for you.

## Regression test
Cite **FND-01**. Whichever way the decision goes, the test must drive **both** paths: a create and an
update, each with `status: "Closed"` and no `closed_date`, asserting the same outcome — and if the
default is kept, asserting that the response states which date was applied.
