# FT-03 — Switching role does not take effect until the page is reloaded
Severity: High | Scenario: FS-23 | Criterion / BRD §: SEC-05, §59, §55 (RoleSwitcher) | Role: any | Status: **Verified** 2026-10-07

The first **product** defect this suite has found. Every previous finding was a defect in the
harness; this one is in the application, and it is the reason FS-23 still fails after H-07 was fixed.

## Steps to reproduce
1. Sign in as any role — say Executive.
2. Change the header's "Act as user and role" picker to an Admin.
3. Do not reload. Look at the picker and the sidebar.

## Expected (CLAUDE.md)
> "Deactivating a user, or removing their role, invalidates an already-issued token on its next
> use." (SEC-05) — and more plainly, the dev sign-in is a **user+role picker** (Part 0, §55): picking
> a role is how you become that role. The screen must then show that role's permissions.

## Actual
The token changes; the application does not. Measured directly, four seconds after switching, with
no reload:

| | token's role (`/api/auth/me`) | picker shows | Admin-only nav ("Audit Trail") |
|---|---|---|---|
| after switching to Admin | **Admin** | `U-040\|Executive` | **absent** |
| after a reload | Admin | `U-001\|Admin` | present |

So the session really is Admin — the server says so — while the UI keeps the previous role's
identity and permissions indefinitely. It is not a slow update: it never converges without a reload.

## Evidence
Reproduced with a throwaway Playwright probe against the running app (not committed); the table
above is its output. FS-23 fails downstream of it: as "Admin" the Import Centre still renders only
the Templates tab, because `can("import:run")` is computed from the stale identity, so there is no
file input to upload the T01 re-import into.

## Root cause
Layer: frontend · Location: `A_Codes/AC_frontend/src/auth/AuthContext.tsx:28` (`signIn`) · Confidence: Likely

`signIn` stores the new token, sets `hasToken`, then calls `qc.clear()`. The identity comes from
`meQuery` (`queryKey: ["me"]`, `enabled: hasToken`). `hasToken` was already `true` before the switch,
so nothing about the query's inputs changes; `qc.clear()` discards the cached entry but does not make
the mounted observer fetch again. `me` therefore keeps its previous value, and because the picker is
a controlled `<select value={current}>` derived from `me`, the UI also snaps the selection back.

Confidence is Likely rather than Confirmed because the precise refetch behaviour of `clear()` with
mounted observers is a library detail I did not step through — but the observable behaviour, and the
fact that only a reload fixes it, both point here.

## Suggested fix
In `signIn`, after `setToken`, make the identity re-read rather than merely dropping the cache — for
example `await qc.refetchQueries({ queryKey: ["me"] })`, or invalidate instead of clear and let the
observer refetch. Clearing the rest of the cache is still right: everything else was fetched as the
previous role.

Worth checking the same pattern in `signOut`, which also calls `qc.clear()`.

## Regression test
Cite **SEC-05**. Assert that immediately after a role switch, with no reload, `/api/auth/me` and the
UI agree: the picker shows the new role and a nav entry gated on a permission only the new role holds
appears. FS-23 then exercises it end to end. A frontend unit test cannot cover this today — there is
no frontend harness (G7.5) — so the functional suite is the only place it can live.

## Verification, 2026-10-07 (functional-tester, Gate 0 exit, commit `f89ef6a`)

**Verified.** FS-23 (`SEC-05 re-importing T01 without a role invalidates that role's session`)
passed twice: in the full suite run against a freshly seeded database (2.6 s), and again in a
targeted re-run against a second pristine database (2.2 s). The scenario depends on the role switch
taking effect without a reload — as Executive the Import Centre renders no file input, so the
upload step cannot even start if the identity is stale.

No reload is involved anywhere in the scenario, and `confirmIdentity` reads the new identity back
from `/api/auth/me` before the scenario proceeds, so a silent non-switch would fail loudly.
