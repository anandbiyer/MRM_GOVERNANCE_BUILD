## 3. Judgements asked for

### Is the "locked/busy" message test a sound discriminator?

**SQLite.** On SQLite it is sound for contention: pysqlite reports `SQLITE_BUSY` (including `BUSY_SNAPSHOT`) as "database is locked". It is too wide in one respect, though. It answers "a reset is already running" for any write-lock contention, including contention from writers that are not resets (TR-79, below).

The filter's other half is untested. The re-raise of a non-contention `OperationalError` is mutant N3, and it survives.

Matching on the text is also weaker than matching `exc.orig.sqlite_errorcode` (Python 3.11+), which is engine-specific and does not depend on the wording.

**PostgreSQL.** The claim blocks rather than erroring, and **that is fine**:
- Under READ COMMITTED, a blocked `UPDATE … WHERE holder IS NULL` waits for the holder's transaction to commit. It then re-evaluates the predicate against the new row version, matches zero rows, and returns `False`, which gives a clean 409. That is the atomic compare-and-set the docstring claims.
- The only transactions that lock the `reset_lock` row are `acquire_reset_lock`, `set_reset_stage`, `release_reset_lock` and recovery. Each commits immediately. The long reset transactions (clear, seed load) never touch the row, so a block lasts milliseconds.
- On PostgreSQL the "locked/busy" branch is effectively unreachable. If someone ever configures a `lock_timeout`, psycopg's "canceling statement due to lock timeout" contains neither "locked" nor "busy", so it would re-raise as a 500. That is a latent edge, folded into TR-80.
- The PostgreSQL path has no test (TR-73, BL.38, not re-raised).

### Could the read-first path answer 409 wrongly?

**Not through the identity map.** `_lock_row` uses `populate_existing`, so the ORM object is overwritten from the row actually returned.

**The remaining staleness is SQLite's WAL snapshot.** `configure_sqlite` emits `BEGIN` on the first statement, and the auth dependency's `db.get(AppUser)` runs first in the same session. So the read-first can see the lock as it was at the start of the request.

- **Snapshot shows held, but the reset finished meanwhile:** the client gets a 409 naming a reset that has just ended. The window is one request's duration, and the error is in the safe direction. **Acceptable; no finding.**
- **Snapshot shows free, but a reset started meanwhile:** the claim cannot match, either because the row's holder is set or because the stale snapshot cannot be upgraded. The client gets a 409, and `_readable` re-reads in a fresh transaction, so the message names the batch. **Correct.**

**There is one real wrong 409** (`false_409_probe.py`, `false_409_probe.txt`):
- Case H: no reset was running at any time, and an unrelated writer held SQLite's write lock for longer than `busy_timeout`. `start_reset` answered **409 "A reset is already running. Wait for it to finish…"**.
- Before the fix this was a 500. It is now a refusal with a false reason.
- Realistic triggers are a long structured import or a document batch commit while an Admin presses Reset. Retrying succeeds.
- `test_g1_32_a_database_lock_on_the_claim_is_a_409_not_a_500` **asserts this exact false message with the lock free**, so the test encodes the defect (TR-79).
- Case W did not produce a false 409: an unrelated commit landed between the auth read and `start_reset`, and the reset was accepted, which is correct.
