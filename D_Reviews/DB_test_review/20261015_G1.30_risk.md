## 3. Thread mode and the questions asked

**Builder's probe re-run.** The probe ran unchanged at 50 ms sampling while my mutation run was
loading the machine, and it **failed**: `t=2.40s reset reads finished but no example report yet`.
I then ran an instrumented copy that records the batch statuses and keeps sampling past a
"finished" reading. At 20 ms it passed 3 of 3 runs. At 2 ms it **failed 5 of 5**, each time with
exactly one sample at about 2.9–3.05 s reading `seed=Completed, documents batch=None`. The end
state was correct in every run: seed Completed, 1,116 documents, 1 report. Two runs of the same
probe disagreed, so the builder's "post-fix no violation" reading depends on the sampling rate
and does not prove the fix holds.

**Cause, which predates G1.30 and lies outside its diff.** `engine.run` → `_record` commits the
seed batch `Completed`. `_reset_job` then opens a new session for `missing_baseline_settings`,
and only after that writes the hold back to `Processing`. Between those commits neither reset
batch is in flight. The comment above the hold says it "closes the gap", but that is true only
of the gap after the hold. GEN-05 ("reports the reset finished only when a further reset would
be accepted") and GEN-04 (overlapping resets) are both open in that window. The window lasts
milliseconds, but a status poll can land in it, and so can a second POST. This is TR-65.

**Does FT-04's ordering test still guard the handover?** Yes (M4). The seed status write moved
into the job, so the test's "no commit after the last submit" now covers `_reset_job` alone.
That is the right scope, because in thread mode the job is the only writer after the handover.

**Can the seed batch latch non-terminal?**
- `staged` is None: no. The analysis is skipped, then the report and the restore run. The
  stage-time spy test exercises this path, and M2 kills it.
- The final restore itself fails: **yes, it latches.** The restore sits outside the `try`.
  `latch_probe_test.py` makes that commit raise `OperationalError("database is locked")`, and the
  batch stays `Processing` with no `error_message` while `reset_in_progress` returns it. The way
  out is `POST /api/imports/batches/{id}/cancel`, since `Processing` is in `CANCELLABLE`. That
  meets GEN-05's escape clause but not "a background job that fails marks its own batch Failed".
  This is TR-67.
- `record_job_failure` fails: it swallows the error by design, so the batch latches and cancel
  is the only way out. This is inherent and acceptable.
- Process killed mid-job (thread mode): the batch latches until it is cancelled. The same was
  already true of the documents batch, so no new exposure.

**Is the "inner reason not overwritten" rule right for the seed batch?** Yes, and it never
triggers here. No path reaches the job with the seed batch already `Failed`: the missing-baseline
path returns before `submit`, and a staging failure raises before it. On an analysis failure the
documents batch carries "Document analysis failed: …" and the seed batch carries
"Seed evidence analysis failed: …", so each batch has its own reason.

**Is marking the seed batch Failed on an analysis failure correct against GEN-05?** Yes. The job
now owns the seed batch (it holds it `Processing`), so it must take it to a terminal state; the
other choice is a latch. Under GEN-05, "a background job that fails marks its own batch Failed
with the reason" now applies to the seed batch. The old outcome was `Completed` over an empty
Document Centre, which was a false green (FT-05's class). One cosmetic cost: the Import Centre
shows the seed batch `Failed` although its template rows loaded. The stage in the message
explains why. This is correct, but no test covers it (M5): TR-66.
