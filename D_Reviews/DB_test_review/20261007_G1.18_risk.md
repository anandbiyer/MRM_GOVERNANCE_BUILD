### REG-16 — **Weak** (the permission half is proven at the route only; the hash probe is narrow)

> "Generating twice from the same data and business date gives the same content hash. Each generation
> writes one audit event. A user without `REPORT_GENERATE` is refused by the API (403); nothing is
> stored and no audit event is written."

| Clause | Test | Verdict |
|---|---|---|
| twice → same content hash | `test_reg_16_the_same_data_gives_the_same_content_hash` (`:170`) | **Asserted for equality**, and not satisfiable by a constant (the third assertion fails a constant hash). But sensitivity is proven for inventory only — TR-04. |
| ...and distinct report ids | `:176` | Asserted. |
| one audit event per generation | `test_reg_16_each_generation_writes_exactly_one_audit_event` (`:188`) | **Asserted** — delta of exactly 1, plus `action`, `entity_id`, `user_id` and `role`. `audit_count` (`tests/conftest.py:127`) guards against a truncated page making "unchanged" true by accident, which is the right shape for this kind of check. |
| 403 from the API | `test_reg_16_a_role_without_report_generate_is_refused_and_nothing_is_stored` (`:202`) | **Asserted** for Executive and Auditor. Scope across the other seven roles unasserted — TR-02. |
| nothing is stored | `:212` (route) and `:277` (service) | **Asserted.** The service-level test (`:258`) is the right instinct and exists precisely because `require()` short-circuits the route — see the caveat in TR-10 about `autoflush=False`. |
| **no audit event is written** | `:213` (route only) | **Not asserted where it matters.** TR-01: an audit event recorded and committed by the service on refusal passes everything. |

Positive note on the implementation, which the tests do pin: the hash deliberately excludes the
predecessor's *identity* but includes the `baseline` (`report_service.py:59`, `:69`), and dropping
`baseline` from the sections fails three tests — so the exclusion list is not a loophole that was
widened until the test passed. The audit event is recorded on the same `Session` before the single
`db.commit()` (`report_service.py:361–365`), so AUD-01's transactional coupling holds structurally;
no test asserts the coupling, which matches the standing §76A.14 gap for AUD-01 and is not a
regression introduced here.

On the question of whether the baseline mechanism itself is proven rather than just its output: the
`baseline`-removal mutation fails `test_reg_15_changes_since_lists_exactly_the_differences`,
`test_reg_16_the_same_data_gives_the_same_content_hash` and the reset test, so the diff genuinely
reads the stored predecessor's baseline. What is *not* distinguished is baseline-diff from a
timestamp window in the specific case the code comment gives as its reason
(`report_service.py:209–212`): two reports in the same second. Both the second and third report in
test 5 would behave identically under a timestamp implementation. I am not recommending a test for
it — with second-granularity `func.now()` it would be awkward and slow to stage — but the reason the
design exists is argued in a comment rather than held by a test, and that is worth knowing.

## 5. Out-of-scope observations (recorded, not graded)

- A reset does not clear `model_risk_report` (it is absent from `reset_service.DELETE_ORDER`,
  `reset_service.py:48`), and `seed_previous_report` returns early if any report exists
  (`report_service.py:393`). So the seeded month-old baseline appears only on a database that has
  never held a report: a demo that generates a few reports and then resets keeps those and gets no
  fresh month-old predecessor. The new test uses a clean fixture, so this path is untested. Benign
  for the first demo run; worth a plan note rather than a finding, and `generated_by` is
  deliberately FK-free (`app/models/reports.py:22–24`) so the reset cannot fail on it.
- `business_date` follows `app.clock.today()` while `generated_at` follows `func.now()` (real wall
  clock) — deliberate and commented (`report_service.py:352–354`), and the right split, but it means
  a report's header shows two clocks. The seeded report pins `generated_at` to a fixed
  `datetime.combine(on, time(9, 0))`, which keeps GEN-01 determinism intact.
- `report_lowest_scoring_limit` is categorised "Dashboard" in
  `B_Inputs/AA_bootstrap/T12_policy_settings.csv:70` and `regulatory_framework` as "Governance
  score" at `:69`. Cosmetic, but the Admin screen groups by that column.
- FS-25 (`A_Codes/AF_e2e/functional/reports.spec.ts`, not run here) adds screen-level reconciliation
  the backend suite does not have — tier counts rendered on the page, band labels never showing the
  internal keys, "Compared against MRR-" — but it is not in CI and does not inspect the PDF bytes,
  so it does not close TR-06.
