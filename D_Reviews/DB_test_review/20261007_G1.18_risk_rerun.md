## 3. Change-by-change judgement

### 1. TR-01 — refused generation writes no audit event (`tests/test_reports.py:409`)

**Holds.** The assertion is at the service, which is the path the CLI and the seed loader take, and
it is the only place the check can be exercised because `require()` short-circuits the route.

Adversarially:

- Count shape is right: `select(func.count()).select_from(AuditEvent).where(entity == ...)` taken
  from the session, not through `/api/audit`, so no page cap can make "unchanged" true.
- `db.rollback()` before the count means the test proves "not **committed**", not "never
  constructed" — the same caveat TR-10 records for the report row (the fixture is
  `autoflush=False`). That is the right reading of "written", so it is not a finding.
- A service that committed the *report* and then raised would be caught: the `ModelRiskReport`
  count assertion survives the rollback.
- Residual: the entity filter. See TR-12.

### 2. TR-02 — who holds `REPORT_GENERATE` (`tests/test_reports.py:443`)

**Holds, and is well constructed.** The expected set is written out as literals rather than derived
from `ROLE_PERMISSIONS`, so the test cannot agree with a wrong matrix. It iterates
`ROLE_PERMISSIONS.items()`, which covers all ten roles including `Admin`'s
`frozenset(Permission) - {SYSTEM_ADMIN}` blanket — so a new permission silently joining Admin is
visible, and a grant to any other role fails. Both directions probed.

### 3. TR-03 — business date, not calendar date (`tests/test_reports.py:457`)

**Holds.** Fails against `date.today()`. The `today() != date.today()` precondition is the detail
that makes it durable: if the two ever coincide the test fails rather than passing for free.

Not covered, and deliberately so: `generated_at` still follows `func.now()` (real wall clock) while
`business_date` follows the business clock. That split is correct and commented
(`report_service.py:352–354`); the seeded report pins `generated_at` to
`datetime.combine(on, time(9, 0))`, which is what keeps GEN-01 reproducible.

### 4. Reset determinism — is it real? (`tests/test_reports.py:471`)

**Real, not accidental.** The load-bearing assertion is the `content_hash` equality across two
resets, and it has teeth: `MUT=seed_nondeterministic` (a wall-clock marker folded into the seeded
report's baseline) **fails** it. The hash covers inventory, validation, findings, approvals, score,
documentation and the full `baseline` — every model id with its phase, tier and name, every finding
status and every approval id — so matching after a second reset genuinely says the regenerated
portfolio is identical. `regenerate_seed_on_reset=True` in the test fixture (`tests/conftest.py:30`)
means the seed **generator** is exercised, not only the loader.

Two honest qualifications:

- `after[0]["report_id"] == seeded[0]["report_id"]` is near-tautological: the seeded id is the fixed
  `MRR-{today-30}-001`, so it holds whenever a seeded report exists at all. No harm; the hash
  carries the proof.
- Only the DELETE_ORDER half of the change is pinned. `MUT=seed_early_return` — the removed early
  return put back — passes all 21 tests, because with `ModelRiskReport` in `DELETE_ORDER` the guard
  is unreachable from the reset path. The removal is therefore untested and, as TR-11 records,
  slightly fragile.
- `MUT=reset_keeps_reports` and `MUT=seed_no_seed` both fail the test, so it does catch the two
  defects it was written for — though the first surfaces as an `IntegrityError`, not an assertion
  (TR-11).

How much of §76A.14's standing **GEN-01 determinism** gap does this close? Partly. Two resets at the
same business date are now compared, which is what that gap asked for, but the comparison is a report
content hash: it covers models, findings and approvals, and says nothing about documents, document
versions, tiering answers, phase history, users or policy settings. Worth recording as "GEN-01
determinism: partly proven" when §76A.14 is next recalculated — not claimed as closed.

The service-side shaping change is also an improvement in its own right: excluding retired models
from `movable` stops one model appearing under both "phase changes" and "models retired", which is
what makes `models_retired == []` assertable; and excluding models already in Development is what
makes the count exactly 3 rather than "3 minus however many were already there".

### 5. TR-05 — exact "changes since" counts (`tests/test_reports.py:396`)

**Holds**, in both the gross and the quiet direction. `findings_opened` is the one change list still
unasserted in the reset scenario — the seeded baseline carries every current finding, so it should be
`[]`. Not a finding: `MUT=changes_opened_unguarded` is caught by
`test_reg_15_changes_since_lists_exactly_the_differences`, which asserts `findings_opened == []` in
the nothing-changed case. One extra line in the reset test would make it exact there too.

## 7. Out-of-scope observations

- A reset clears the `model_risk_report` **rows** but not the stored JSON objects. Report ids are
  reused across resets (`MRR-<business date>-001`), so the next generation overwrites the orphan blob
  at the same path with freshly computed content. Benign on `LocalStore`; worth knowing if the demo
  ever runs against a MinIO bucket with object-lock or versioning, where the `put` would behave
  differently.
- The pre-existing `test_reg_16_the_service_refuses_an_unpermitted_principal_too` and the new
  `test_reg_16_a_refused_generation_writes_no_audit_event` now overlap substantially. Leaving both is
  fine — the older one carries the "permitted role goes through" control for the *report row* — but a
  reader should know they are one check split in two.
- `report_lowest_scoring_limit` is still categorised "Dashboard" and `regulatory_framework`
  "Governance score" in `B_Inputs/AA_bootstrap/T12_policy_settings.csv:69–70`. Cosmetic; the Admin
  screen groups by that column.
- The baseline-versus-timestamp design argument (`report_service.py:209–212`) is still argued in a
  comment rather than held by a test — two reports in the same second behave identically under either
  implementation. Not worth a test; worth knowing.
