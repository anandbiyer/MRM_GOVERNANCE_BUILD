## 3. Answers to the questions asked

**Does the every-commit test guard the window class?** Yes, with one narrow tolerance.
- It listens on `Session` `after_commit`. Nothing under `app/` commits through `engine.begin()`/`connect()`, so every product commit is observed. That closes the FT-04 residual about Engine-level commits for this test.
- Lock state changes only at commits, so sampling after every commit covers every state another session could see. Inline order matches thread order, because the holder token is passed through both `submit` calls and nothing is released between them.
- It kills A and G, and the builder's inference mutant.
- The tolerance is "claim ≤ 1": one commit may come before the claim because the fixture's `create_all` database has no lock row. On a database that has the row, one business commit before the claim would pass (TR-77).
- It also does not see non-database side effects before the claim, which is mutant H.

**Can any path leave the lock held in-process?**
- **`release_reset_lock` raising:** it cannot. It catches `Exception` and logs. If its commit fails, the lock stays held until the next start (P3), which is documented.
- **`set_reset_stage` raising:** every call is inside a `try` that releases (P4, and the parametrised test).
- **Inline vs thread mode:** both have the same ownership transfer.
- **`missing_baseline_settings` path:** it releases correctly, but no test would notice if it stopped (B).
- **`start_reset` failing before submit:** it releases correctly, but this is also untested (C).
- **`runner.submit` raising:** the lock **stays held** (P1, P2). Both `submit` calls sit outside any `try`/`finally`. The realistic trigger is the executor refusing work at interpreter shutdown, and the next start recovers it, so this is Low (TR-75).

**Is the claim atomic on PostgreSQL?** By construction, yes. `UPDATE … WHERE lock_id = 1 AND holder IS NULL` under READ COMMITTED takes the row lock. A concurrent claimant blocks on it, then re-evaluates the predicate against the committed row and matches 0 rows. Under REPEATABLE READ or SERIALIZABLE it would raise a serialisation error instead, but the application uses the default. `_ensure_lock_row`'s insert race is absorbed by its `IntegrityError` handler. **No test shows it**, though. The atomicity test is sequential, mutant D passes everything, and `test_postgres.py` has no lock test (TR-73). BL.12 is closed in code but not in evidence.

**Does FT-04's ordering still hold with the new stage writes?** Yes. The last write before the handover is `set_reset_stage(…, "Seed evidence analysis")`, and nothing is committed after `submit`. Mutant G is killed by the ordering test and by the every-commit test. The job's own lock writes (the stage, then the release) run sequentially inside the job, so they cannot race it.

There is one new interaction, and it does **not** endanger the running job: a refused claim is a zero-row UPDATE, which appends nothing to the WAL. The probe confirms this, with 4/4 runs ending with all 1,116 documents and the report. The interaction does hurt the refused caller (TR-70).
