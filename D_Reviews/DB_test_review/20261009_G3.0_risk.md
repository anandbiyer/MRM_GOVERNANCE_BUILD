## 3. Question 2 — is the CI wiring right? Can the job pass vacuously?

### 3.1 It fails closed where it matters

Verified by execution, not by reading:

| Condition | Exit | Effect on the job |
|---|---|---|
| Base ref unresolvable (simulates an unfetched `base.sha`) | **1** | Job fails, with `fatal: bad object` quoted. Correct: fails closed. |
| No arguments | **2** | Job fails. |
| Findings present | **1** | Job fails. |
| `python` non-zero inside a `run:` block | — | GitHub's default `bash -e {0}` propagates it; I confirmed `bash -e` aborts the block. |

`fetch-depth: 0` is present and is **required** — without it the base sha is not in the shallow clone
and the job would fail closed on every run. So that part is right, and right in the safe direction.

### 3.2 It can pass vacuously — three ways

1. **`workflow_dispatch` is always green.** For a manual run `github.event.before` is **empty**, which
   falls into the all-zero branch: `case "" in *[!0]*) ;; *) exit 0`. I tested the shell logic directly —
   `base=''` → `EXITS 0 (treated as first push)`. Every manual dispatch prints *"First push on this ref —
   nothing to diff"*, which is also untrue, and reports success. `workflow_dispatch` is a declared
   trigger, and a manual re-run is exactly what a human does when a job looks wrong. (TR-52)
2. **The job never runs during a gate.** `on: push: branches: [main]` — so pushes to
   `gate-1-core-report` do not trigger it. It runs only on a pull request, or on the eventual push to
   `main`. Whatever the job proves, it proves it once at the end, not while the work is being done. That
   matters a great deal here, because of §3.4 and §8.
3. **`base == head`** gives an empty diff and exit 0. Not reachable through either trigger today; noted
   for completeness.

The all-zero guard itself is near-dead: because `push` is filtered to `main`, the only genuine
"first push on this ref" is main's very first push, which has happened. Its practical effect is to
swallow `workflow_dispatch`.

### 3.3 The base ref should be the merge-base, not `base.sha`

`github.event.pull_request.base.sha` is the base-branch tip in the event payload, not the fork point.
`git diff <main tip> <PR head>` therefore also reports files changed **on main** since the branch
diverged, with main's content as the "pre-change" side — content that will never be in `_OLD/`, giving
false failures the PR author cannot fix.

Today the two agree: main has four commits not in this branch (`0f11fda`, `575314a`, `b997c32`,
`e274111`) and all four touch only `E_ProjectPlan/` and `CLAUDE.md`, so
`git diff --diff-filter=M main HEAD` and `git diff --diff-filter=M $(git merge-base main HEAD) HEAD`
return identical 39-file sets. The defect is **latent, not theoretical**: the first time a Gate 2
decision row touches a covered file, every open PR starts failing on it. (TR-54)

### 3.4 The job fails on this branch today — and seven of the eight are noise

Running the **product script** on the range the Gate 1 pull request would use:

I traced every one of the eight commit by commit, separating merge commits from hand edits. The common
cause is `19389be` — *"Merge main into gate-1-core-report: Gate 0 closed and merged"*. For a file the
merge changed, the branch-side parent content was never a hand-edit starting point, so no snapshot
exists and none should. Example, `T12_policy_settings.csv`:

| Commit | Kind | Pre-state | Snapshot |
|---|---|---|---|
| `8cf87ff` | edit | `f783764467` | `T12_policy_settings_v8_20261007.csv` |
| `58a6a71` | edit | `74db0ee973` | `T12_policy_settings_v9_20261007.csv` |
| `19389be` | **merge** | `0686fa8074` | none — and correctly so |

**Seven of the eight are merge artefacts.** The eighth is real: `reset_service.py` at `d18f984`
("G1.18 Done: close the checkpoint's three High findings, and TR-06") is an ordinary 7-insertion,
3-deletion hand edit whose pre-state `30542e7d82…` I searched for across **every** `_OLD/` tree in the
repository — `A_Codes/_OLD`, `B_Inputs/_OLD` and the root `_OLD` — and it is absent. That is a sixth
instance of the convention breach, on a file that pre-dates the branch, found by this tooling and by no
one before it. Credit where due: the control works.

But the operational consequence is bad. CLAUDE.md records that `gate-1-core-report` was branched from
`review-agents` and says *"merge `main` into `gate-1-core-report` before its own gate review"* — so the
merge is mandatory, and the job it will meet cannot go green. A build control nobody can get green is
disabled or overridden, which is the same ending as one that fails open. The author's own stated worry
about the merge hook ("that is exactly how the merge hook once shipped failing open") applies here with
the sign reversed. (TR-49)

### 3.5 Can the job be made to pass vacuously — summary answer

Yes, three ways (§3.2), of which `workflow_dispatch` is the practical one. It cannot be made to pass
vacuously through a *missing* ref, a missing argument or a crash — those all fail closed, which I
verified. The two silent skips in §2.2 (`d`, `g′`) are not vacuous passes of the whole job, but they are
vacuous passes of individual files, and neither is visible in the output: the skipped file is not
counted in "Checked N modified file(s)".

## 4. Question 3 — is the documented limitation correct, and is it stated where it will be read?

### 4.1 The claim is correct, and I tried to disprove it

The script says it proves the base content is recoverable, "not that every intermediate edit was
snapshotted", which "no post-hoc check can verify". I attempted the stronger check: for every
**non-merge** commit in `main..HEAD`, require that commit's pre-state be recoverable from `_OLD/` at
head. It found **9** unsnapshotted committed edits across 22 commits.

Those 9 do **not** all represent missing snapshots, and that is the point. `snapshot.sh` copies the
*working tree* before an edit; when several edits happen between two commits, the snapshot it writes may
match no committed state at all. `report_service.py` shows this cleanly — `_OLD/` holds
`report_service_v1_20261007.py` through `v3`, taken during the G1.16–G1.18 session, yet none of them
matches the pre-state of `26bd74a`, `c2eb7e9`, `58a6a71` or `d18f984`:

| Commit | Pre-state | Snapshot matching it |
|---|---|---|
| `8cf87ff` | (added) | n/a |
| `26bd74a` | `e1ca9bd5` | none |
| `c2eb7e9` | `6a0756bc` | none |
| `58a6a71` | `87e05a7b` | none |
| `d18f984` | `0a0c4969` | none |
| `2d50219` | `7be46230` | `report_service_v5_20261009.py` |
| `860403b` | `eff2f22f` | `report_service_v6_20261009.py` (recovered by G3.0) |

So snapshots were being taken; they simply do not land on commit boundaries. A per-commit checker cannot
tell "no snapshot was taken" from "a snapshot was taken of an uncommitted intermediate state", and it
reports both. **The row's limitation claim stands, and my attempt to beat it produced exactly the
unactionable noise the claim predicts.** I would tighten only the wording: the unverifiable part is
specifically *uncommitted* intermediate states.

### 4.2 Where the limitation is stated — and the one place it is not

Honest in three places: the module docstring (lines 13–17), the commit message, and the G3.0 plan row's
Evidence column. The runtime messages are also carefully worded and do not overclaim — the success line
is *"Every one has its pre-change content in `_OLD/`"*, a statement of what was proved, not "the
convention was followed". That is the right instinct and worth keeping.

It is **not** stated in Part 0's convention text, which is where a developer reads the rule. Part 0 still
describes snapshotting as a manual habit and does not mention that CI now checks it, what the check
proves, or what it does not. The docstring is reachable only by invoking the script with no arguments.
(TR-57)

## 5. Question 4 — does the script need tests? Yes, and the repository already argues the case

`A_Codes/AZ_tools/` contains no tests. The precedent is `.claude/hooks/test_review_gate.py`, whose own
docstring makes the argument better than I can:

> *"They were ad hoc before, which is how the 2026-10-06 repair shipped failing open: a heredoc turned
> `\b` into a literal backspace in six places, `GIT_PUSH` matched nothing, and a real push to main was
> ALLOWED. The deny path has to be tested, not only the allow path, and testing it by hand is how it
> gets skipped."*

That is this script's situation precisely, and G3.0 did not follow its own repository's precedent. The
validation in the commit message is a hand check against seven commits — the very method the hook test
exists to replace — and §2.1 shows it is already unreproducible.

**Minimum set.** Follow `test_review_gate.py`'s shape exactly: a single self-contained runner,
`python A_Codes/AZ_tools/test_check_snapshots.py`, building throwaway git repositories under the system
temp directory, never in this repository. Not pytest: `pytest.ini` sets `testpaths = tests` under
`AB_backend`, and this tool does not belong there. Fifteen cases, every one of which I have already
executed by hand in this review, so each is known to be writable and known to discriminate:

*Must detect (the deny path — two of these fail today):*

1. Modified file, no snapshot → fail, and the output **names the file**.
2. Snapshot with the right name, **different bytes** → fail, and the output names the near-miss copy.
3. Correct bytes in the **wrong `_OLD/` directory** → fail.
4. `B_Inputs/AA_bootstrap/*` modified without a snapshot → fail.
5. **Rename + rewrite** without a snapshot → fail. *(Fails today — TR-53.)*
6. **Non-ASCII filename** modified without a snapshot → fail. *(Fails today — TR-53.)*

*Must allow (the allow path — two of these fail today):*

7. Correct snapshot present → pass, exit 0.
8. CRLF working tree against an LF snapshot → pass.
9. `B_Inputs/AC_seed/` and `B_Inputs/AD_demo_files/` modified without snapshots → pass.
10. Added-only and deleted-only change sets → pass.
11. Extension-less file, dotfile and two-dot stem, each with a `snapshot.sh`-named snapshot → pass.
12. **Mode-only change** with no content change → pass. *(Fails today — TR-55.)*
13. A range containing a **merge commit** whose merge-brought files have no snapshot → pass.
    *(Fails today — TR-49. This is the case that decides whether the job is usable.)*

*Must fail closed:*

14. Unresolvable base ref → non-zero.
15. No arguments → non-zero.

Cases 5, 6, 12 and 13 are the ones worth writing first: each is a real defect found in this review, and

One more thing the test file should assert, which no case above covers: that `check_snapshots.py`'s

nothing ties them together.

## 6. Question 5 — should the convention have an acceptance criterion, and where?

**Yes, and its absence is the root cause of the recurrence, not a side note.** §76A.14's grep contract —
"a criterion ID appears in a test file only where a test actually verifies it" — is what makes coverage
visible. Part 0's convention appears in no criterion, so it appears in no coverage table, so the only
instrument left was a reviewer reading `git log`. Five reviews, five catches by eye, and two of those
reviews broke it while fixing it. A control with no criterion is a control with no coverage signal.

**Where.** Not §76A: that section is the governance core, and this is a repository control, not a
business requirement. **§76E** is already the right home — §76A.14 reserves it for §64/§65, and the
20261008 report proposes `PLT-01` there for the UTC-timestamp invariant. Keep §76E as
*"Platform, build and file-handling controls (PLT)"* and add the build controls to it rather than opening
a §76F for three criteria. **`PLT-01` is taken** by the timestamp criterion, so these take the next free
IDs. Proposed text, for the owner to accept or amend — I do not edit CLAUDE.md:

> ### PLT-02
> For every file modified under `A_Codes/` or `B_Inputs/` in a change set, the content it had before the
> change set is recoverable from the matching `_OLD/` directory, matched by content with line endings
> normalised. `_OLD/` itself, `B_Inputs/AC_seed/`, `B_Inputs/AD_demo_files/`, and added and deleted files
> are excluded. A change set that does not satisfy this fails the build. Changes a merge commit brings in
> are not hand edits and are not required to have snapshots.
>
> ### PLT-03
> The snapshot check fails closed: an unresolvable base ref, a missing argument, or a path it cannot
> classify fails the build rather than passing it. No trigger reports success without having compared two
> resolvable refs, and every modified covered file is either checked or reported as unchecked — never
> silently skipped.

`PLT-02`'s last sentence and the whole of `PLT-03` are not satisfied today (TR-49, TR-52, TR-53), so
writing them has the usual effect: the criterion fails first, then the fix lands. That is the right
order, and it is why the criteria should be written **before** the fixes rather than after.

Worth recording alongside: the merge-to-`main` hook (`.claude/hooks/review_gate.py`) has 27 hand-run
checks and also no criterion, and `A_Codes/AB_backend/tests/test_migrations.py` still maps to none
(TR-46, open). §76E should take all three in one pass.

## 8. The headline: the job cannot detect the finding it closes

CR-54's three findings were missing snapshots of `report_service.py`, `test_reports.py` and
`0007_model_risk_report.py`. None of the three exists on `main`:

```
report_service.py          ABSENT on main
test_reports.py            ABSENT on main
0007_model_risk_report.py  ABSENT on main

$ git diff --name-status main HEAD -- <those three>
A   A_Codes/AB_backend/app/services/report_service.py
A   A_Codes/AB_backend/migrations/versions/0007_model_risk_report.py
A   A_Codes/AB_backend/tests/test_reports.py
```

All three are **`A` (added)** in the range the CI job diffs, and added files are excluded by design —
reasonably so, since the convention is about editing something that already existed. So on the Gate 1
pull request the job would report **8 findings, none of which is CR-54**, while the three findings it
was built for are invisible.

This is not a flaw in the matching logic, which is good. It is the gap between the granularity the
script is correct at — a single commit, where the author snapshots and then commits, so snapshot and
commit boundary coincide — and the granularity CI gives it. The script's own validation set is seven
single commits, and at that granularity it is exactly right. Nothing runs it there.

The fix follows from that sentence: **run it per commit, at commit time.** `/build-row` already ends
each row with a commit, which is the natural hook, and the pre-commit position is the only one where the
working tree still holds what `snapshot.sh` captured. Keep the CI job as a backstop for pre-existing
files, with merges skipped, and it stops producing noise.
