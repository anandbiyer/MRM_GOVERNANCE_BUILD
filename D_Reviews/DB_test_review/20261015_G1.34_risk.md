## 4. Specific questions from the caller

**Does a real `generated_at` for the seeded example change anything that relied on it being earlier?**
No. I checked each item:
- **`latest()` / `list_reports()` ordering, and the predecessor after a reset.** A reset deletes every
  `model_risk_report` first (`DELETE_ORDER` starts with `ModelRiskReport`) and writes the seeded example
  last, under the lock. So the example is the only report and the newest at that moment. Every later
  generation gets a `func.now()` that is the same or later. CR-67 now also refuses generation while the
  lock is held, so nothing can be created while the reset is running.
- **Ties at one-second granularity.** A user generating in the same second as the seed write is possible
  in tests. The tie-break `report_id DESC` resolves it correctly: the seeded id is
  `MRR-<business date − 30>-001`, and any generated id is `MRR-<business date>-nnn`, which always sorts
  higher. `test_reg_17_a_reset_seeds_one_earlier_report…` (reset, then generate immediately) asserts
  that the seeded example is the predecessor, and it passes. M8 shows that the inverse ordering is caught.
- **`previous_generated_at`.** This value now carries the reset's real time instead of `2026-08-31 09:00`.
  Neither the screen nor the PDF renders it (both show `previous_report_id`), and it lies outside the
  hash (`changes_since` is excluded). Its naivety (PLT-01 / BL.31) is a separate, existing problem that this row
  neither causes nor fixes.
- **REG-17 newest-first.** `test_reg_17_earlier_reports_are_listed_newest_first` is unaffected (it runs
  on `loaded_client` and has no seeded example). The reset-then-generate path is covered by M8.
- **GEN-01 reset-twice.** `test_gen_01_a_reset_clears_the_report_history_and_reseeds_it` compares
  `report_id` and `content_hash`, and `content_hash` excludes `generated_at`, so the comparison is
  unaffected. It passes under M1, M7 and M8 as well. The seeded `generated_at` now differs between two
  resets. That is intended by D17, and GEN-01 asks for row counts and the distribution, not timestamps.
- **Dates seen side by side.** Under `MRM_TODAY_OVERRIDE` the seeded example now shows a real
  wall-clock "generated at" (for example 2026-10-15), "computed on 2026-09-30" (`figures_as_of`) and
  "dated 2026-08-31". Every generated report shows the same wall-clock / business-date split, and D17
  option (a) chose this, so it is an observation and not a finding.

**Is `seed_previous_report` correctly *not* refused?** Yes, by construction. It never calls `generate`.
It builds its row directly, and the check lives only in `generate`. It runs under the lock, which
`test_g1_32_a_second_reset_during_the_report_write_is_refused_409` asserts is held at that point. If it
were ever routed through `generate`, the reset would fail at the "Seeded example report" stage, and
`test_reg_17_a_reset_seeds…`, `test_s12_…`, `test_d14_…` and `test_d17_…` would all fail.

**Does the 409 leak whether a reset is running to an unauthorised caller?** Not through the API. The
route depends on `require(Permission.REPORT_GENERATE)`, which answers 403 before the service runs. In
the service, the check comes after the permission check, as the comment says. However, M3 shows that
nothing asserts that order (TR-110). Separately, `GET /api/admin/reset/status` is readable by any
authenticated user (`CurrentPrincipal`), so "a reset is running" is not a secret anyway. The 409 message
reveals the stage and nothing more.
