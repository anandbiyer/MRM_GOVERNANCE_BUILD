## 4. `test_api_timestamps.py` — should it have a criterion, and where?

**Yes, and the author was right to record the gap rather than invent a tag.**

First, the test discriminates. I neutered `app/schemas/core._as_utc` by swapping its code object — which
is the function `AfterValidator` holds a reference to, so this restores the pre-BL.28 behaviour without
touching the file — and `test_bl_28_every_api_timestamp_is_timezone_aware` **fails**, naming the offending
fields (`/api/models/M-0003.model.created_at = 2026-10-08T10:53:09`, `…/api/admin/policy[0].updated_at`,
and the rest). The other two tests pass under that mutation, correctly: they guard the opposite
directions (a date-only field must not gain a time; an already-aware value must not shift). The
`assert checked > 10` guard stops the sweep going vacuous. This is a well-built test.

Where the criterion belongs: **§76E**, the set §76A.14 already proposes for BRD §64 and §65, not a stretch
of an existing ID. The behaviour is a platform serialisation contract, and it is the proximate cause of a
user-visible governance defect — §67 asks "When did it happen?" and the app answered with two different
calendar days for events minutes apart. Stretching INV-02 or LIF-01 ("timestamp", "transition date") would
be wrong: those are about the record carrying the field, not about how it is serialised, and the stretch
would bury the contract inside a criterion nobody reads for it.

Proposed text, to sit with the §64/§65 criteria in a new §76E:

> **PLT-01** — Every timestamp the API emits carries a UTC offset, and a date-only field never acquires
> a time. One event renders as one calendar day on every screen, in any browser timezone. A new
> timestamp field is covered by declaring its type.

Tag `test_api_timestamps.py`'s three tests and **FS-29** with it. Note what PLT-01 would then expose:
the existing endpoint sweep does not satisfy its own third sentence — see **TR-40**.

**The resolution was right.** Keeping this branch's GEN-01 row over `main`'s is correct: `main`'s copy
says determinism is unasserted, and since G1.18 that is false —
`test_gen_01_a_reset_clears_the_report_history_and_reseeds_it` does compare a second reset at the same
business date with the first. Keeping it at **Weak** rather than promoting it is also right.

I re-derived how much it proves, with two new seed mutations:

| Mutation | Caught? |
|---|---|
| `seed_portfolio_nondeterministic` — the whole seed drawn from a clock-dependent RNG (`RANDOM_SEED` from `time.time_ns()`), so tiers, phases, owners, validations, findings and approvals all move between the two resets | **yes** — `test_gen_01_…` fails |
| `seed_phase_nondeterministic` — **one** model's `lifecycle_phase` alternates between the two resets, everything else identical | **yes** — `test_gen_01_…` fails |

(The narrow one must be made to alternate deterministically. A first version flipped on
`time.time_ns() % 2` and passed, because both resets happen inside one test and landed on the same
parity — a 50 % coin toss. Worth recording: a mutation that only *sometimes* differs proves nothing
either way.)

So the determinism proof has real teeth at single-model granularity. Two clauses of the entry need
tightening:

1. **"which covers … and the report baseline"** is true of the implementation and asserted by nothing.

   otherwise treat the breadth as guaranteed.
2. **"says nothing about documents … tiering answers"** is slightly too strong in both directions.
   Document *completeness* (`completeness_pct` and `models_missing_documents`) and the *derived* tier are
   inside the hash; what is uncovered is the document and document-version rows themselves — about 1,100
   evidence files, the bulk of a reset — and the four tiering answers behind the tier. Policy settings
   are covered only where they reach a figure (score band boundaries, the lowest-scoring limit).

## 6. FS-29 — does the version on disk discriminate, and is the pattern anywhere else?

### 6.1 FS-29: the offset assertions carry the proof, and they do discriminate

Re-derived rather than taken from the row. `functional/dashboards.spec.ts:226-290`:

- The three `toMatch(/(Z|[+-]\d\d:\d\d)$/)` assertions run a regex over the **raw API response text**
  (`score.calculated_at`, every `phase_history[].changed_at`, `audit[0].occurred_at`). They share no
  mechanism with the page, so a naive API fails them regardless of what the page does. The backend
  equivalent of exactly this check fails under my `naive_timestamps` mutation (§4), which is independent
  confirmation. **These discriminate.**
- The three `localDay(...)` comparisons do **not** discriminate against a naive API, and the comment in
  the file says so in terms. They still catch a page rendering the wrong instant or a hard-coded date.
  Correctly described.

### 6.2 But the time-of-day assertion is order- and state-dependent — **TR-41**

`expect(overview, "a lifecycle entry must show a time, not just a date").toMatch(HAS_TIME)` is scoped to
the **whole `main`**, and Model 360's Overview tab renders a second `formatDateTime` value: the tier
override list, `Model360Page.tsx:85`. The seed creates no tier overrides (`generate_seed.py` has none), so
on a freshly reset database the lifecycle list is the only thing on that tab with a time, and the
assertion has teeth — which is why the author saw it fail when `changed_at` was sent through `formatDate`.

The problem is that **FS-08 applies a tier override to M-0012** (`functional/inventory.spec.ts:148-176`,
"Exposure run-off (functional suite)"). `playwright.config.ts` sets `workers: 1, fullyParallel: false`, so
file order is alphabetical and `dashboards.spec.ts` runs before `inventory.spec.ts` — today, first time
through, on a fresh database. But there is no reset in `functional/helpers`, so the suite run *after* FS-08
has run — a re-run without a reset, or a `-g` invocation, or any reordering — leaves M-0012 carrying an
override line with a time, and the assertion passes while `changed_at` goes through the date-only
formatter. It is one state change away from the TR-25/TR-26 failure mode it was written to avoid.

Fix: scope it. `page.locator("section.panel", { has: page.getByRole("heading", { name: "Lifecycle" }) })`
for the Overview assertion, and the audit table for the History one.

### 6.3 The same pattern elsewhere: one more instance, in FS-25 — **TR-39**

I checked every date derivation in the functional suite:

| Site | Expected value derived from | Shares the defect's mechanism? |
|---|---|---|
| `dashboards.spec.ts:104-158` (FS-26) — `parts()` vs `isoParts()` | digit **sets** split out of the ISO string | no — sound |
| `dashboards.spec.ts:207` (FS-28) — `new Date(y, m-1, d).toLocaleDateString()` | the three ISO components, built as local midnight | no — sound. The defect is misparsing the *string*; this never parses it. (It does compare a Node-formatted string against Chromium output; if the two locales ever differed it would fail loudly, not pass vacuously.) |
| `dashboards.spec.ts:253` (FS-29) — `page.evaluate(new Date(s).toLocaleDateString())` | the page's own clock | **yes** — and declared non-load-bearing in the file |
| **`reports.spec.ts:51-57` (FS-25) — the REG-16 determinism check** | **the element that already holds the first report's hash** | **yes, and not declared** |

FS-25's REG-16 check is the one to fix:

```ts
const first = await hashOf();
await page.getByRole("button", { name: "Generate report" }).click();
await expect.poll(hashOf, { timeout: 30_000 }).not.toBe("");
expect(await hashOf(), "REG-16: same data, same business date, same content").toBe(first);
```

`hashOf()` is never `""` once any report is displayed, so the poll returns on its first evaluation —
before the second generation can have rendered. The final assertion then normally compares the **first**
report's hash with itself, which cannot fail. Nothing asserts the second generation happened at all: the
`dbCount("model_risk_report")` check brackets only the first click. Fix: assert
`dbCount("model_risk_report") === before + 2` after the second click, and poll for the displayed report
id to change before comparing hashes. The criterion itself is not at risk —
`test_reg_16_the_same_data_gives_the_same_content_hash` is strong and CI-gated — so this is Medium, about
what the scenario is worth as evidence.
