## 2. The two mechanisms I was asked to challenge

### 2.1 `import_service.record_job_failure` writes a batch status with no audit event

**Verdict: correct as written. I would not add an audit event.** Four reasons, in order of weight:

1. **It cannot join a transaction.** The function exists to run *while an exception is already in
   flight*, opens its own session, and swallows its own failures on purpose
   (`app/ingestion/service.py:36-64`, docstring and the bare `except Exception` at `:63`). AUD-01 is a
   requirement about coupling — "in the same transaction as the business change, so the two commit or
   roll back together". There is no business change here to couple to: the business writes of the
   crashed job were rolled back when its session closed unconsumed. An audit event written in a
   separate session would assert a coupling that does not exist.
2. **§58's event list does not contain it.** The list is of governance events (create, update,
   delete/retire, import, upload, extraction, confirmation, rejection, approval, tier override,
   threshold change, …). "Import" is on it, and the import *is* audited — at the point a user starts
   it (`app/ingestion/service.py:193`), when a batch is uploaded (`:151`), when a file's template is
   remapped (`:172`) and when a user cancels (`:207`). The machine-set outcome status is not a
   governance event; it is the §42 batch state field.
3. **It matches the precedent exactly.** `engine._record` has written `batch.status`,
   `batch.error_message` and the per-file statuses with no audit event since the first build
   (`app/ingestion/engine.py:195-216`), and that was examined and accepted in both prior reviews —
   recorded as spec issue **S5** (Part 0's "the only place that writes" wording is the inaccurate
   part, not the code). Adding audit to the new function alone would make the two paths inconsistent.
4. **Adding it would widen the failure surface of a recovery path.** The docstring's reasoning is
   sound: losing the original exception to a secondary failure inside the recorder is worse than not
   recording the status.

Two caveats, neither changing the verdict, both small enough to be Low:

- **An inconsistency inside the same feature.** The reset's *other* failure mode — an incomplete seed
  policy — **does** audit, as `action="reset_incomplete"`
  (`app/services/reset_service.py:168-170`). So one way for a reset to fail leaves an audit event and
  the other does not. If anything should change, it is that the two agree.
- **The record is overwritable and is the only one.** `batch.error_message` is the sole trace of the
  crash, and `_record` reassigns it unconditionally (`app/ingestion/engine.py:197`:
  `batch.error_message = failure`, where `failure` is `None` on a clean run), while `"Failed"` is in
  `EDITABLE` (`app/ingestion/service.py:29`) so a crashed batch can be re-validated. Re-running a
  crashed batch therefore erases the record of the crash with nothing in the audit trail — a §67
  ("What happened?") gap rather than a §58 one.

The guard at `app/ingestion/service.py:58` (`if batch.status == "Failed" and batch.error_message:
return`) is right: nested recorders do not paper over a more specific reason.

### 2.2 `CANCELLABLE = EDITABLE + ("Validating", "Processing")`

**On the permission check: still correct, and unchanged.** Both cancel paths keep their server-side
check as the first statement — `app/documents/batch.py:420` calls `_require_review` (`DOCUMENT_REVIEW`,
the permission G0.3 added), and `app/ingestion/service.py:202` calls `_require_import` (`IMPORT_RUN`).
`CANCELLABLE` is only consulted *after* the permission check, so widening it cannot widen who may
cancel; it widens only *when* an already-permitted caller may do so. No router changed in these five
commits (`git diff 280864b..779e3de -- app/api/` is empty), so the authorization surface is identical.
The front end remains display-only.

**On cancelling something mid-write: there is no corruption path, and no partial write.** Each job
owns one outer transaction and commits once at the end; `cancel` runs in the request session and
touches only `import_batch.status`. Nothing in the codebase ever *reads* the Cancelled status —
`grep -rn "Cancelled" app/` returns four hits and three of them are the writes and the status
vocabulary (`app/documents/batch.py:424`, `app/ingestion/service.py:206`,
`app/models/ingestion.py:10`, `app/services/reset_service.py:53`). So:

- No job polls for cancellation, so a cancel never interrupts a loop part-way. The import engine's
  single `db.commit()` (`app/ingestion/engine.py:145`) and the document storer's per-item SAVEPOINTs
  under one outer commit (`app/documents/batch.py:376-404`) are untouched. **Nothing can be left half
  written by a cancel.**
- But the cancel is then **silently undone**: `_record` and `_confirm` each write a terminal status at
  the end of the job (`engine.py:204-216`, `batch.py:396-403`), overwriting `"Cancelled"`. A user who
  cancels a loading import sees `Cancelled`, and a moment later the batch reads `Completed` with the
  data loaded, having written an audited `cancel` event that had no effect. That is CR-30.
- On SQLite the cancel can also fail outright. `_confirm` takes the write lock at its first SAVEPOINT
  flush and holds it until the final commit — for a reset's evidence batch that is 1,116 files — so a
  cancel issued inside that window waits `sqlite_busy_timeout_ms` (5,000 ms by default,
  `app/config.py:24`) and then raises, where before it returned a clean 409.

**Does this reopen FT-05's own problem?** No. The case FT-05 is about is a batch whose job is *dead*,
where nothing holds a lock and no later write overwrites the status — and that is precisely the case
`test_ft_05_a_batch_left_non_terminal_can_be_cancelled` (`tests/test_documents.py:432`) exercises. The
widening is correct for its purpose. It is the *live*-job case that is unguarded, and no test covers it.

## 11. Verdict input

The gate's substance is closed. The Critical is fixed, and fixed the right way — by ordering rather
than by locking, with the reasoning written into the code where the next person will meet it, and with
the in-flight signal continuous across the handover so FT-02's fix is not traded for FT-04's. CR-21's
fix is better than the one I proposed: it removes the phase names entirely instead of adding a fourth
key beside three literals, it makes "Initiation requires nothing" a consequence rather than a special
case, and it corrects my own mistaken claim about `CONTEXT_KEYS` — a claim which, had it been followed,
would have left four settings unguarded. CR-22's recovery is real and I verified it byte for byte
rather than taking the commit's word. The amended snapshot rule is a genuine clarification, not a
convenience: the seed workbook is reproducible from files that are snapshotted every time.

On the two mechanisms put to me: `record_job_failure` is right not to audit, and I would push back on
a change there — it runs with an exception in flight, in its own session, with no business write to
couple to, and it matches a precedent two reviews have already accepted. The one thing I would tidy is
that the reset's *other* failure mode does audit, so the feature is internally inconsistent.
`CANCELLABLE` is also right for the case it was written for, and the permission check is untouched and
still correct; what it exposes is that `Cancelled` has never meant anything to a running job, and the
widening turns that from unreachable into reachable.

One finding stands in the way, and it is procedural rather than functional: **G0.23 edited
`app/documents/batch.py` and `app/services/reset_service.py` without snapshotting them**, so the
post-G0.22 state of both — including the FT-04 ordering fix as first written — exists only in git.

Gate 0 run rated it High. I have kept the severity for consistency: the convention is one of two that
Part 0 says override normal practice, and three consecutive reviews have now caught the same lapse by
hand. It is also two commands to fix, and nothing is lost.

cancel that is recorded but not honoured (CR-30), the failure wrapper that does not cover the reset

and preferably add the mechanical check so a fourth review does not find the same thing. CR-30, CR-31
and CR-32 to the Backlog; CR-32 with S9 attached, because it needs a decision rather than a fix.
