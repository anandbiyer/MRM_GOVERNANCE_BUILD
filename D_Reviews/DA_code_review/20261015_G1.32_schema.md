## 3. Findings

| ID | Severity | Criterion / table | Problem | Suggested fix |

| CR-59 | Low | §48 `reset_lock`; CR-42 (FK naming) | **The stated reason for having no FK is wrong for `batch_id`.** The model docstring (`app/models/reset_lock.py:9-11`), the migration (`0008_reset_lock.py:11-12`) and §48 (`claude.md:2292-2294`) all say `batch_id` and `acquired_by` "point at rows the reset itself deletes and reloads". That is true of `acquired_by` (`AppUser` is in `DELETE_ORDER`, `reset_service.py:60`) but not of `batch_id`: `ImportBatch` is not in `DELETE_ORDER` (`reset_service.py:58-60`), and nothing in the reset deletes import batches. Leaving `batch_id` without an FK is still defensible: the lock should not depend on batch-history housekeeping, and a later purge of import history must not fail on the lock row. Only the documented reason is inaccurate, and a future maintainer could act on it. | Pick one. (a) Correct the three texts: `acquired_by` has no FK because the reset deletes users; `batch_id` has none so the lock never blocks or depends on import-history housekeeping. (b) Or add a named `sa.ForeignKeyConstraint(["batch_id"], ["import_batch.batch_id"], name="fk_reset_lock_batch_id_import_batch", ondelete="SET NULL")` to both ORM and migration. (a) is the smaller change and keeps the design as reviewed. |
| CR-60 | Low | §48 `reset_lock` ("always 1; one row") | **The singleton is a convention, not a constraint.** Nothing stops a second row (`0008_reset_lock.py:28-39` has no CHECK), and `last_outcome` takes any string. This is harmless today because every read and write filters `lock_id == LOCK_ID` (`reset_service.py:132, 158, 173, 191, 231`), but §48 states it as a property of the table. | Optional: add `sa.CheckConstraint("lock_id = 1", name="singleton")` to both ORM `__table_args__` and the migration (renders `ck_reset_lock_singleton`). Optionally also a CHECK on `last_outcome IN ('Completed','Failed','Interrupted')`. Both sides must carry it, or neither, for the drift guard. |
| CR-61 | Low | §48 `reset_lock`; drift guard coverage | **§48 says the row is "inserted by migration 0008" (`claude.md:2274`), but only migrated databases get it that way.** `create_all` databases (the dev launcher, every SQLite test via `tests/conftest.py:47`) get it lazily from `_ensure_lock_row` (`reset_service.py:136-144`). | CR-62 | Low | Part 0 Commands; §66 readable errors | **A dev `dev.db` started without the launcher has no `reset_lock` table.** Part 0 documents starting the backend directly (`uvicorn app.main:app --reload --port 8000`).
