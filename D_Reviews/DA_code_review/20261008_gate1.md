### 2.2 The content hash excludes the predecessor's identity and includes the baseline — confirmed

`report_service.py:59` names the two excluded keys and `:62-73` is the hash:

```python
_NOT_CONTENT = ("previous_report_id", "previous_generated_at")

content = {k: v for k, v in sections.items() if k != "changes_since"}
content["changes_since"] = {k: v for k, v in sections["changes_since"].items()
                            if k not in _NOT_CONTENT}
```

So: `baseline` is **in** (it survives the first comprehension, which drops only `changes_since`);
the predecessor's id and timestamp are **out**; the change *lists* stay in. That is the rule at
`claude.md:971-975`, exactly.

I traced the two-generation case by hand rather than trusting the comment. Generation 1:
`previous=None`, so `changes_since` is the `empty` dict (`:229-230`) and `_approvals`'
`seen_before=None` gives `decisions_since_previous=[]`. Generation 2: `previous` is report 1, whose
stored baseline equals the current one, so every change list comes out empty and `seen_before`
contains every approval id, so `decisions_since_previous` is `[]` again. After the two exclusions the
canonical forms are identical. The hash matches, and both reports are still stored separately — which
is why the schema checkpoint was right to refuse a unique constraint on `(business_date, content_hash)`.

Determinism is also robust where it easily might not have been: every list in every section is
explicitly sorted (`:98`, `:122`, `:143`, `:151`, `:181`, `:192`, `:240-253`), `json.dumps` uses
`sort_keys=True`, `_plain` normalises `Decimal` and `date` so neither depends on `repr` (`:42-52`),
and `Completeness.missing` is a list ordered by the policy's required-document list
(`app/rules/document_rules.py:148`) rather than a set — so no iteration order leaks into the hash
across processes. Proven by `test_reg_16_the_same_data_gives_the_same_content_hash`
(`tests/test_reports.py:170`), with the sensitivity probe's weakness already carried as BL.7/TR-04.

### 2.4 The seeded previous report without evidence documents — challenged

The reordering itself is **right** and I would not change it. FT-04's rule ("the reset makes no
database write after submitting a background job") is the most expensive lesson in this repository's
log, and `report_service.seed_previous_report` before the handover is the only placement that obeys
it: `_reset_job` stages the evidence batch, restores the seed batch's status, and only then calls
`doc_batch.start_analysis_job` (`app/services/reset_service.py:195-225`). Putting the report after
the handover would re-create FT-04 precisely.

But **two of the three reasons given for the consequence do not hold**, and the consequence is bigger
than the comment says.

1. **"They did not exist then" is not true.** The comment at `reset_service.py:203-206` justifies the
   missing documents as right "for a report dated 30 days earlier (they did not exist then)". The
   seed's ~1,100 evidence files are dated across the whole governance history, not the last 30 days —
   the Monitoring folders alone run `2026_Q1`/`2026_Q2` (BL.23 records that a regeneration moved them
   from Q2 to Q3). A report dated 2026-08-31 for a portfolio whose evidence goes back quarters should
   show most of that evidence, not none of it.
2. **REG-16 is not the criterion in play.** REG-16 is about two generations *from the same data on the
   same business date* (`claude.md:3590-3593`); it says nothing about seed ordering. The criterion
   that actually requires this to be reproducible is **GEN-01**, and it is satisfied for a different
   reason: `DELETE_ORDER` clears `model_risk_report` first (`reset_service.py:51`) and the evidence is
   deleted with it, so the seeded report is regenerated from the same document-free state every time —
   which is what `test_gen_01_a_reset_clears_the_report_history_and_reseeds_it` proves by comparing
   content hashes across two resets (`tests/test_reports.py:483-505`). Determinism is not what forces
   the ordering; FT-04 is. Worth correcting the comment, because the next person to touch this will
   reason from it.
3. **The consequence is three sections, not one.** With no documents on file,
   `document_rules.completeness` returns `score=0` rather than `None` for every model whose phase
   requires documents (`app/rules/document_rules.py:146-150`), so the documentation component scores
   **0** at its full 25% weight (`governance_view.py:98-111`, `:126`) instead of being dropped as
   not-applicable. In the seeded report that moves:
   - `documentation.completeness_pct` → **0** (`report_service.py:199`);
   - `documentation.models_missing_documents` → **every** model with phase requirements, which in the
     PDF is a table of that many rows (`app/reports/pdf.py:138-143`);
   - `score.by_band`, `score.portfolio_score` and `score.lowest` → materially depressed across the
     whole portfolio.

   The demo effect is a board report dated a month ago reading 0% documentation and a much lower
   portfolio score, and the next report's "changes since" cannot explain the jump, because the diff
   covers only models, phases, findings and approvals. A viewer reads an improvement that did not
   happen. This is CR-41 (Medium), with a fix that keeps FT-04 intact.

   The service's own docstring also still asserts the opposite — "The *figures* in the seeded report
   are today's. That is honest for demo data and is the only thing available" (`:389-391`) — which was
   true when it was written and is not now.
