## 2. The four things the caller asked to be challenged

### 2.1 G1.26's job ordering — the FT-04 reading is right; the G0.18 guard is not

**Your reading of FT-04 is correct.** FT-04 is about writes made by `_reset_job` *after* it has
handed work to a background job, because in thread mode those commits race the job for SQLite's
write lock. Work done inside a job the reset started is not that. The code satisfies it literally:
`runner.submit(_store_evidence_then_seed_report, …)` is the last statement of `_reset_job`
(`app/services/reset_service.py:220`) and nothing follows it. The existing ordering test still
proves this, and it now finds the last handover rather than naming the job, which is the right
repair (`tests/test_imports.py:547-557`). The staging-before-handover arrangement you relied on is
intact (`reset_service.py:195-220`).

**The G0.18 guard does now have a window.** Trace it:

| Step | Seed batch (`source="reset"`) | Documents batch (`source="seed"`) | `reset_in_progress` |
|---|---|---|---|
| `stage_seed_documents` returns | `Processing` (`:197`) | created, non-terminal | in flight |
| status restored | `Completed` (`:210-213`) | non-terminal | in flight |
| `analyse_job` → `_analyse` → `_confirm` commits | `Completed` | **`Completed`** (`app/documents/batch.py:397-403`) | **None** |
| `seed_previous_report` runs | `Completed` | `Completed` | **None** |

`_analyse` calls `_confirm` synchronously when the batch was staged with `auto_confirm`
(`batch.py:280-283`), and `_confirm` writes the terminal status and commits before returning. Only
then does `_store_evidence_then_seed_report` call `report_service.seed_previous_report`
(`reset_service.py:223-233`). That call is a full `sections(db, None)` — `dashboard_service.summary`
plus `governance_view.portfolio` over the whole portfolio, the most expensive computation in the
application, with a <2 s budget of its own (§64) — followed by an object-store put and a commit.

So for a second or two: both batches terminal, `reset_in_progress` → `None`
(`reset_service.py:106-118`), `GET /api/admin/reset/status` → `in_progress: false`
(`app/api/admin.py:38-46`), and `start_reset` would accept a second reset (`:130-135`). That is
FT-02's defect — "the caller cannot tell when a reset has actually finished" — reopened on the
last write of the reset, and G1.26's plan row claims the opposite (`project_plan.md:169`: "which
keeps FT-04's rule … and G0.18's (no window where nothing is non-terminal)").

It is a regression, not an inherited gap: in the previous ordering `seed_previous_report` ran at
`_OLD/AB_backend/app/services/reset_service_v11_20261009.py:207`, between the status hold at `:197`
and the restore at `:220`, i.e. while the seed batch was non-terminal. **CR-53.**

No test can see it. Every test forces `MRM_JOB_MODE=inline`, so by the time
`test_ft_04_a_reset_leaves_the_seed_batch_terminal_and_the_evidence_loaded` asserts
`in_progress is False` (`tests/test_imports.py:575`) the report has already been written;
and `test_the_reset_batch_stays_in_flight_until_the_evidence_is_loaded` observes the status inside
the stager (`:485-499`), which is before the window opens.

### 2.2 `is_seeded` as a stored column — I agree, and for a stronger reason than the one given

Keep it. The argument in the commit message ("no user generated this" ≠ "this is a shaped example")
is right, and there is a concrete case behind it: `report_service.generate` explicitly supports
`principal=None` for the CLI and seed paths (`report_service.py:331-339` — the permission check is
skipped when `principal is None`), so the day anything else generates a report without a principal,
a derived flag would label a real report as an example on screen. A disclosure that can become
false by someone adding an unrelated call site is not a disclosure.

The deeper reason is that the two statements are about different things. `generated_by` is
provenance of the *row*; `is_seeded` is a statement about the *content* — that the baseline inside
the stored copy was shaped and therefore that the next report's "changes since" is manufactured.
Nothing in the row or in the stored JSON expresses that otherwise. The cost was a column edited
into a migration that has not reached `main`, which is close to nothing, and §48 was updated in the
same change (`claude.md:2215-2217`). The ORM, the migration and the schema agree: `Boolean`,
`nullable=False`, `default=False`, `server_default=false()`
(`app/models/reports.py:36-37`, `migrations/versions/0007_model_risk_report.py:50`,
`app/schemas/governance.py:393-395`).

One observation rather than a finding: nothing ties the flag to the shaping. `is_seeded=True` is
written only by `seed_previous_report` (`report_service.py:434`), by convention. That is fine while
one function shapes baselines; if a second ever does, the flag is the thing that must move with it.

### 2.3 What the hash still covers — the exclusion is not too wide, and it is one figure too narrow

**Not too wide, confirmed.** `content_hash` drops exactly one key:
`{k: v for k, v in sections.items() if k != "changes_since"}` (`report_service.py:74`). `_NOT_CONTENT`
is gone. Everything else is in: `inventory`, `validation`, `findings`, `approvals`, `score`,
`documentation` and `baseline`. Baseline inclusion matters and is intact — it is a `sections[...]`
key like any other, so it survives the comprehension. The determinism machinery I checked last time
is unchanged (every list sorted, `sort_keys=True`, `_plain` normalising `Decimal` and dates). S10
licenses exactly this and the code does exactly this.

**But one figure inside the hash is derived solely from the predecessor.**
`approvals.decisions_since_previous` is computed from `seen_before`, the set of approval ids in the
*previous stored report's* baseline (`report_service.py:139-160`, `:303-306`). S10's reasoning —
"if the predecessor's identity is provenance, so is everything computed from it" — applies to it
word for word, and it lives in a section the hash covers because REQ-REG-10A files "decisions since
the previous report" under Approvals (`claude.md:951`). So the placement is right and the hash is
wrong, which is why the fix missed it.

The failure is the same shape as FT-09:

| Generation | Predecessor | `decisions_since_previous` | Hash |
|---|---|---|---|
| A | seeded example (baseline holds every approval) | `[]` | h1 |
| *(a decision is recorded — `POST /api/approvals`)* | | | |
| B | A (baseline predates the decision) | `[X]` | h2 |
| C | B (baseline holds X) | `[]` | h3 ≠ h2 |

B and C are generated from identical data on the same business date and hash differently. REG-16 as
reworded — "the same data and business date gives the same content hash over the report's figures" —
fails. **CR-52.**

Your three identical hashes through a real reset could not have exposed this: nothing recorded an
approval between the generations, so the list was empty throughout. Nor can the new regression test:
`test_reg_16_the_hash_ignores_which_report_came_before` seeds the predecessor with
`seed_previous_report`, whose shaping touches only `baseline["models"]` and `baseline["findings"]`
(`report_service.py:408-422`) and leaves every approval id in place, so all three generations see
`seen_before` ⊇ every approval and produce `[]` (`tests/test_reports.py:560-584`). That is precisely
the criticism G1.25 made of the test it replaced: the fixture passes, not the code.

than S10 licenses, and every Part 0 invariant but the snapshot one holds. CR-52 and CR-53 are both
small changes — an allowlist for the digest, and a `finally` inside the job that already exists.
